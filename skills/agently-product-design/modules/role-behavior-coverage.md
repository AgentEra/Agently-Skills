# 角色与行为覆盖

先执行[统一入口](../SKILL.md)的共同方法。用于多角色职责、权限、状态或交接会改变结果的场景，也用于用户明确要求行为穷尽；简单文案修正不强制建矩阵。此模块设计覆盖范围，不充当多 Agent 调度器。

选择足以暴露差异的角色，不固定人数。角色应在目标、知识、权限、设备或责任上有实质区别：例如创建者、执行者、只读协作者、新手、迟到或返回者。同一个人在不同阶段也会有不同需求。角色视角不等于必须启动多个 Agent。

对每个角色写：想达成什么、已知什么、当前看见什么、可以做什么、什么才算完成，以及系统不能替他作出的决定。避免所有人轮流同意的顺利演示。

先选一个有代表性的端到端主故事，再加入影响最大的变体，避免对所有角色×设备×状态做无意义穷举：

- 首次进入→发现入口→操作→看到反馈→下一人接手→结果找回。
- 误操作、取消/撤销、拒绝/有条件接受、权限不足、失败重试。
- 长内容、空/加载状态、窄屏或键盘操作等与产品有关的限制。
- 涉及持久化或协作时，补刷新/重开、断线重连、晚加入、版本变化或并发冲突。

每条故事至少写出角色与触发、前置数据、连续动作、各步预期反馈、可观察的业务结果。将关键断言关联故事 ID 和步骤。不能把“点到了最后一个按钮”当完成。

检查动作之间的语义：提交不一定是批准，批准不一定是执行，生成不等于审阅，接收不等于同意，编辑不等于拥有。具体效力按目标产品定义，不移植某个项目的会议阶段。

## 有边界的“穷尽”

先声明角色、对象/版本、权限、状态与动作的有限范围，以及不在范围内的条件。按业务不变量和风险检查状态转移、允许与拒绝路径、交接、取消/重试/重复/过期及恢复；并发与外部事件只在场景适用时纳入。不能把每个维度机械做笛卡尔积。

使用“角色及已知信息→前置状态→动作/事件→允许条件→预期反馈与后置状态→下一责任人→证据”的覆盖视图，沿用已有故事和问题 ID。区分未设计、已设计未执行、已执行通过、失败和范围外；归并等价场景时说明不变量与代表性依据，高风险边界独立保留。

有限样本和静态角色模拟不等于所有真实行为穷尽或真人可用性测试。缺接口、账号、设备或真实调用时标记具体未覆盖条件；不能用模拟替代权限与数据一致性的运行证据。

方案模块用它检查责任与业务闭环；应用模块将场景落到功能、交互和视觉；文档模块只取读者知识、阅读/执行路径和所需决定。模型节点的数据和执行状态细节交给 `agently-agentic-design`，不按用户角色数创建模型节点。
