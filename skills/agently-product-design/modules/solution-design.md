# 方案设计：从需求与原因选择机制

先执行[统一入口](../SKILL.md)的共同方法，已读不重复。用于新方案、实质重设计或方案取舍；不是每次局部修复都要填写的报告。检查范围按决定的影响扩大，不为凑章节调查全项目。

## 先观察真实任务

查现有需求、现场记录、操作路径、任务样本与失败证据，必要时核对用户。围绕实际角色目标记录：任务怎么开始与结束、输入/输出、复杂度、规模与频率、哪些可并行、哪些有真实依赖、协作如何发生、在哪里等待或返工。标明来源、样本范围、时间/版本与未知项；一次事故只能证明该次事件，不能据此估算常态频率或容量。

涉及协作制度本身的设计时，辨明业务诉求、任务、交付增量、发布与责任承接的实际关系。Coding Agent 的进度记录及交接规则由已安装的 `agently` 维护；本模块只评估这些机制如何满足当前产品场景，不默认某个项目的会话或发布流程。多角色职责、权限与状态改变结果时读取[角色与行为覆盖](role-behavior-coverage.md)。

已有流程、分支、角色、接口与实现提供现状和可行性材料。先问任务为什么需要某步，再判断机制是否保留。区分：

| 条件类型 | 如何处理 |
| --- | --- |
| 业务必须满足 | 说明来源及效力，如用户授权边界、数据完整性或必须由谁决定；不是从旧按钮反推业务规则 |
| 当前实现限制 | 标明版本与证据、绕过或改变的成本；不能把暂时没有接口视为新机制不能设计 |
| 可重选的历史设计 | 用任务和效果检验继续保留、简化或替代；既不自动继承，也不无依据推翻 |

明确要求从需求重设计或破坏性重构时，先建立任务/结果模型，再评估目标机制；旧结构用于解释迁移，不作为候选空间边界。保留/改动授权仍按用户范围执行；设计新能力不等于已经获准上线它。

评审通过建立的是当前有效、可追溯且可修订的执行基线，不是后续事实不会推翻方案的保证。区分已验证约束、暂用假设与待验证问题；对影响范围大且证据弱的假设先做有界验证，或明确验证时点、失败分支与允许先行的独立工作。后置发现必须有反向路径：保存事实与证据→判断影响→决定修改代码、局部计划、单项Spec或公共约束→由有权者确认必要变更→更新版本和覆盖关系→重验受影响部分。不要为适配错误实现而改验收，不因轻微实现调整重审全部，也不静默改公共结论。无样本时不估造方案被推翻的概率；记录实质变更频次、发现阶段与返工量后再判断。

## 建立可追溯的因果与机制联系

每个主要选择能回答：观察到了什么困难；原因是已证实还是假设；目标改变什么；候选机制如何处理原因；效果从哪里观察；要付出什么、依赖什么、什么情况下会失败；如何验证和修正。可在原问题项内写短段落，复杂问题用[共用记录](../assets/delivery-review.md)的决策链视图。

角色表、流程图、API 清单可以解释机制，不能代替上述论证。怀疑原因时给出区分解释的检查或小范围验证，不把改善后的现象自动归因于新机制。量化收益须有计算依据与测量条件；没有基线就给观察方法或待核对目标，不能编数字补完整。

梳理技术架构默认交付 SVG 逻辑分层图；流程图按业务职能分块并区分主次链路，具体采用[架构与流程图表达](../references/diagram-and-board.md#架构与流程图的默认表达)。

设计流程与架构时，先按[关系与边界的必查项](../references/diagram-and-board.md#关系与边界的必查项)核对逻辑、系统边界、职责归属及模块关系，再安排图的节点与连线。先明确规则与数据的权威来源、决策者、执行者和跨边界接口，避免把“接入某系统”误当作“该系统拥有全部业务规则”，或把模块拆分误当作责任转交、独立服务部署。

## 在同一需求基准上比较

按实际有意义的选择比较，适用时包含维持现状/小改；不为简单问题凑固定数量候选。共同框架包括目标任务、场景和边界、业务约束、机制、预期效果、成本/风险、前提与未验项。技术新颖或图更美不自动代表更合适。

- 对齐需求、任务样本、数据/状态、评价维度及证据深度。界面比较还要对齐内容、实际容器/视口、主题、字号等；不能用浅色短内容与深色错误态直接排名。
- 调查本次决定所需的现状范围，不能把三个问题组件当成完整组件库；未知明确标出。现状与目标使用可对照的职责/任务层级，必要时分别给现有实体视图与目标机制视图，通过映射解释关系，不要求两者沿用相同结构或组件数。
- 按稳定名称/编号标明保留、新增、调整、移动、合并/拆分、移除；移动说明去向，移除说明职责取消依据或承接。映射服务于解释变化和迁移，不成为保留历史实体的强制条件。
- 先给可比较的全局关系，再分层展开重点与证据。复杂对象不全塞进一张大图/巨表；总览与详细名录可通过稳定 ID 追溯。简单决定用文字或短表即可，不强制配图。
- 无法对齐的条件写明差异及结论限制；关键数据缺失时给条件性选择和补证据计划，不强行排名。

## 选择、表达与实施验证

建议写清为何选择、适用前提、未决条件、实现缺口、迁移/回退或失败处理（适用时）及可观察验收。新接口等标为目标能力，说明要核实或实现什么，不将其写成当前存在。沿已授权范围推进，不把每个方案判断变成额外审批。缺事实时列出需核对的信息并继续可做工作；“提交可评审材料”不自动意味着要让用户批准调查焦点、评价框架或普通资料读取。只将确实需要选择的业务规则、方案取舍或授权范围列为待决定事项，不凭空设审批关口。

形成评审或方案正文时进入[文档表达](document-expression.md)，让未参与会话的决定者看清观察、问题原因、解决机制及其理由、效果与代价和验证；只保留结论或图表不够。需要实际应用设计/实施时进入[应用体验](app-experience.md)验证机制、连续任务和运行画面。写清楚与跑通都只是各自证据，不互相替代。
