# 方案设计：从需求与原因选择机制

先执行[统一入口](../SKILL.md)的共同方法，已读不重复。用于新方案、实质重设计或方案取舍；不是每次局部修复都要填写的报告。检查范围按决定的影响扩大，不为凑章节调查全项目。

## 先观察真实任务

查现有需求、现场记录、操作路径、任务样本与失败证据，必要时核对用户。围绕实际角色目标记录：任务怎么开始与结束、输入/输出、复杂度、规模与频率、哪些可并行、哪些有真实依赖、协作如何发生、在哪里等待或返工。标明来源、样本范围、时间/版本与未知项；一次事故只能证明该次事件，不能据此估算常态频率或容量。

涉及协作制度本身的设计时，辨明业务诉求、任务、交付增量、发布与责任承接的实际关系。Coding Agent 的进度记录及交接表达由 `agently-collaboration` 维护；本模块设计交付内容与验收，不默认某个项目的会话或发布流程。多角色职责、权限与状态改变结果时读取[角色与行为覆盖](role-behavior-coverage.md)。

已有流程、分支、角色、接口与实现提供现状和可行性材料。先问任务为什么需要某步，再判断机制是否保留。区分：

| 条件类型 | 如何处理 |
| --- | --- |
| 业务必须满足 | 说明来源及效力，如用户授权边界、数据完整性或必须由谁决定；不是从旧按钮反推业务规则 |
| 当前实现限制 | 标明版本与证据、绕过或改变的成本；不能把暂时没有接口视为新机制不能设计 |
| 可重选的历史设计 | 用任务和效果检验继续保留、简化或替代；既不自动继承，也不无依据推翻 |

明确要求从需求重设计或破坏性重构时，先建立任务/结果模型，再评估目标机制；旧结构用于解释迁移，不作为候选空间边界。保留/改动授权仍按用户范围执行；设计新能力不等于已经获准上线它。

评审通过建立的是当前有效、可追溯且可修订的执行基线，不是后续事实不会推翻方案的保证。区分已验证约束、暂用假设与待验证问题；对影响范围大且证据弱的假设先做有界验证，或明确验证时点、失败分支与允许先行的独立工作。后置发现必须有反向路径：保存事实与证据→判断影响→决定修改代码、局部计划、单项Spec或公共约束→由有权者确认必要变更→更新版本和覆盖关系→重验受影响部分。不要为适配错误实现而改验收，不因轻微实现调整重审全部，也不静默改公共结论。无样本时不估造方案被推翻的概率；记录实质变更频次、发现阶段与返工量后再判断。

## 业务流程的完整性与变更影响

设计或实质修订跨角色、跨阶段的流程时，先走完业务，再写正文或画图。从真实触发开始，直到结果交到需要它的人手里，或明确结束、暂缓及恢复条件。沿用原故事或计划，逐个关键步骤回答：

- **从哪里来，谁负责？** 输入是什么、依据哪个版本，谁有权决定或执行，哪个业务模块维护这项事实？
- **这一步留下了什么，下一步怎样用？** 写清产生的决定、状态或成果，记在哪个已有对象或版本，由谁在什么条件下读取并行动。无需持久记录的临时动作可直说；不为补表新建数据库或实体。没有后续使用者时，核对它是否是终点、重复记录或遗漏的交接。
- **没走正常路径怎么办？** 按业务事实区分实际处置：已覆盖、部分覆盖、新增或改变范围，可能产生不同结果。逐个核对接手人、暂缓和恢复条件、拒绝或取消后的去向，以及谁要收到什么结果。处置名称和数量由场景决定；消息送达不能替代接手、办理或业务验收。

**分开判断归属、依赖和时机。** 在哪项工作中听到建议，不决定它归哪项交付；归属不同也可能阻塞当前交付。分别检查它改变谁的范围或标准、谁必须等它的结果、何时由谁获准处理。用[角色故事板](role-behavior-coverage.md#主动用故事板检验业务规则)把这些条件分别改变，检验部分选择、延后等结果能否独立成立。

**原事项结束后仍要办理的工作，应能独立找回。** 用已有的持久记录保留来源、后续行动、责任或待承接状态及办理条件。区分关闭前检查未结义务、确认关闭后询问是否继续、取得相应授权后承接新工作；原事项的授权不自动延续。建议、业务决定、办理回执按各自来源和版本分别留据，可在同一系统保存；本次不继续或未回复，不自动等于拒绝需求或取消他人正在办理的工作。

当反馈暴露出漏掉一种处置、责任或后续使用者时，不等用户继续枚举。追查同类决定的其他出口，沿引用向前找依据、向后找受影响的角色、模块、设计、接口、计划与验收；把每个受影响环节补到原清单，沿完整故事走通后再局部复验。单纯排版差错没有改变业务含义时，只复验呈现。

计划确需调整时，按结果选择：已有阶段能覆盖就修订该阶段；新增结果可独立交付验收时再加阶段；支持工作可单独承接时标明产物、接收方及是否阻塞交付。比较不变更与变更的后果。区分未开始、在途、已验收的工作：说明谁有权使新计划生效、在途工作是否继续或交接、原验收对哪个版本仍有效、哪些变化要重新验收，以及谁负责回告。候选不覆盖有效计划；未知影响显式待核，不擅自停工或重开历史。

依据：[NASA 系统工程手册 §6.2：需求管理](https://www.nasa.gov/reference/6-2-requirements-management/)要求保持双向追溯、评估变更影响并维护基线与处置记录。以上是对产品设计的应用；决策权限沿用实际项目，不预设审批机构或固定流程。

## 建立可追溯的因果与机制联系

每个主要选择能回答：观察到了什么困难；原因是已证实还是假设；目标改变什么；候选机制如何处理原因；效果从哪里观察；要付出什么、依赖什么、什么情况下会失败；如何验证和修正。可在原问题项内写短段落，复杂问题用[共用记录](../assets/delivery-review.md)的决策链视图。

角色表、流程图、API 清单可以解释机制，不能代替上述论证。怀疑原因时给出区分解释的检查或小范围验证，不把改善后的现象自动归因于新机制。量化收益须有计算依据与测量条件；没有基线就给观察方法或待核对目标，不能编数字补完整。

梳理技术架构默认交付 SVG 逻辑分层图；流程图先核对业务职责与交付依赖，再选择重点阅读的路径，具体采用[架构与流程图表达](../references/diagram-and-board.md#架构与流程图的默认表达)。

设计流程与架构时，先按[关系与边界的必查项](../references/diagram-and-board.md#关系与边界的必查项)核对逻辑、系统边界、职责归属及模块关系，再安排图的节点与连线。先明确规则与数据的权威来源、决策者、执行者和跨边界接口，避免把“接入某系统”误当作“该系统拥有全部业务规则”，或把模块拆分误当作责任转交、独立服务部署。

## 在同一需求基准上比较

按实际有意义的选择比较，适用时包含维持现状/小改；不为简单问题凑固定数量候选。共同框架包括目标任务、场景和边界、业务约束、机制、预期效果、成本/风险、前提与未验项。技术新颖或图更美不自动代表更合适。

- 对齐需求、任务样本、数据/状态、评价维度及证据深度。界面比较还要对齐内容、实际容器/视口、主题、字号等；不能用浅色短内容与深色错误态直接排名。
- 调查本次决定所需的现状范围，不能把三个问题组件当成完整组件库；未知明确标出。现状与目标使用可对照的职责/任务层级，必要时分别给现有实体视图与目标机制视图，通过映射解释关系，不要求两者沿用相同结构或组件数。
- 按稳定名称/编号标明保留、新增、调整、移动、合并/拆分、移除；移动说明去向，移除说明职责取消依据或承接。映射服务于解释变化和迁移，不成为保留历史实体的强制条件。
- 先给可比较的全局关系，再分层展开重点与证据。复杂对象不全塞进一张大图/巨表；总览与详细名录可通过稳定 ID 追溯。简单决定用文字或短表即可，不强制配图。
- 无法对齐的条件写明差异及结论限制；关键数据缺失时给条件性选择和补证据计划，不强行排名。

## 按可见收益拆解交付阶段

先问：**如果后续阶段都暂缓，这一阶段交到谁手里，他现在能独立完成哪件原来办不到或很难办的事？如何当场证实？** 这里的“可见”指受益方能观察到改变，不限于界面变化。例如，值班人员能自行恢复一次失败的作业，也是一项收益。一次就能交付并验收的工作不必硬拆。

1. **先列效果，再定顺序。** 从当前可用的起点、最终目标和真实角色出发，用动作与结果给阶段命名。首期选范围小但从头到尾能用的一件事；后续阶段说明在前一期之上多解决什么。可缩小人群、场景或操作种类，不能删掉该场景必需的入口、交接、权限或结果。按收益优先级、真实依赖和待验证风险排序，不预设阶段数，也不按数据库、接口、界面、联调各切一期。
2. **先写每阶段怎么整体验收，再列明细。** 写一段验收故事：谁在什么条件下从正常入口开始，如何操作，交给谁，在哪里看到或再次找到结果；只加会改变判断的异常、限制或比较基线。明确本期必须通过什么，哪些效果留到以后。若只能靠作者代填数据、跳过另一角色或借用下一期能力才能演示，调整范围或合并相邻阶段。
3. **把工作分配到效果之下。** 用一张短表先交代「阶段｜受益方能完成的事｜整体验收条件｜当前状态」，每阶段下再列「明细任务及负责方｜本期交付物｜前置成果／可并行项｜完成条件与证据」。共享底座写清被哪个阶段消费，单纯准备工作不是已交付收益。同一任务可以分期贡献不同成果，不必复制任务或等整个模块做完。已有候选先核对版本、集成位置与验证范围；阶段顺序不要求所有明细串行，也不强制每期单独上线。
4. **用整条故事结算。** 在同一可用版本和约定环境中走通关键路径，记录实际观察。任务全部打勾、接口通过或版本已部署，都不能替代阶段验收。必要效果有缺口时，保留已通过的成果，重开受影响项；沿原故事复验。优先级或范围改变时，在原计划记录效果移到了哪里、为什么、需要补验什么，保留旧结论适用的版本。进展汇报引用这份计划，不另建一份状态表。

例如，预约系统可以先交付“访客能预约一个空闲时段并找回确认结果”，再交付“访客能改期，原时段重新开放”。第二期可用两个账号核验：原访客看到新时段，另一人可以预约刚释放的旧时段。如果只能改页面上的日期，就不能算改期已交付。

## 选择、表达与实施验证

建议写清为何选择、适用前提、未决条件、实现缺口、迁移/回退或失败处理（适用时）及可观察验收。新接口等标为目标能力，说明要核实或实现什么，不将其写成当前存在。沿已授权范围推进，不把每个方案判断变成额外审批。缺事实时列出需核对的信息并继续可做工作；“提交可评审材料”不自动意味着要让用户批准调查焦点、评价框架或普通资料读取。只将确实需要选择的业务规则、方案取舍或授权范围列为待决定事项，不凭空设审批关口。

形成评审或方案正文时进入[文档表达](document-expression.md)，让未参与会话的决定者看清观察、问题原因、解决机制及其理由、效果与代价和验证；只保留结论或图表不够。需要实际应用设计/实施时进入[应用体验](app-experience.md)验证机制、连续任务和运行画面。写清楚与跑通都只是各自证据，不互相替代。
