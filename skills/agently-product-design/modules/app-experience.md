# 应用交互规范、体验走查与逐项改进

从角色目标与已知信息出发，将连续用户任务、发现的问题、设计、实现和复验串成可追溯记录。沿项目规范检查功能、动线、信息组织与实际画面；能完成任务只是基本条件，还要判断过程是否省力、关键信息是否易于理解和找回。

先执行[统一入口](../SKILL.md)的共同方法；已读过无需重复读取。本模块用于应用设计与运行验收。页面主体按[共用审读与修订规则](../references/common-review.md)检查；只有正文起草或长文结构需要调整时才读[文档表达模块](document-expression.md)。

## 严格遵从：界面任务的完成门槛

本节及本 Skill 的验收流程是强制规范，不是可选建议。执行界面实现/整改时必须：

1. 先确定当前用户任务、有效设计基准及同类页面；核对公共控件、页面骨架、表面/底色、密度与响应式的维护归属。复用主题与基础控件不代表页面组合已经统一；禁止按页面另造相同用途的容器、底色和控件变体。
2. 视觉验收前**必须读取并执行**[截图判读与跨页一致性流程](../references/walkthrough-guide.md#严格执行截图判读与跨页一致性)，对实际运行画面形成“具体观察→标准/预期→判断→修订或通过证据”。展示/保存截图只是取证，不能直接勾选通过。
3. 同时对照采用稿/规则及同类已统一页面；保留对象、状态、真实容器、主题/字号和代表内容量的可比条件。合理业务变体必须说明依据，不得用“局部页面”或“组件库默认”解释规范漂移。
4. 发现必验缺陷后继续修正并按原路径复验；缺证据保持待验。功能、交互、视觉分别成立后才能宣布相应范围完成；不得把视觉发现/检查交给用户，不得把“待用户确认视觉”作为开发完成。

按影响范围执行，不为单点改动穷举无关页面；也不能以范围小为由跳过受影响的状态。已授权的例行修订直接推进，不新增无依据的批准流程。

## 页面主体的理解验收

任务、评审、需求和页面主体说明必须执行共用规则的信息自闭环走查。必要背景属于任务内容；具体字段、状态和操作后果按当前页面核验。正文理解通过不能代替下述运行验收。

## 1. 接手并确定本轮完成条件

先读项目自己的约定、当前交接和已有 checklist，确认源码/分支、未提交修改、运行实例、数据与设计基线。复用有效记录，保留稳定编号；不要另起一份互相矛盾的“最新清单”。

用简短文字记录目标、允许修改范围、产品必须保留的约束、可用验证条件与本轮完成判据。区分用户明确要求、已验证事实、工作假设和审美偏好。信息可从项目查明时直接查；真正影响权限、业务规则或不可逆操作的缺口才询问，同时推进独立工作。

按现状选择深度：

| 现状 | 本轮主要产物 | 可作出的结论 |
| --- | --- | --- |
| 从零设计 | 角色场景、故事、状态与界面方案、验收清单 | 设计候选；尚无运行验收 |
| 建立/统一交互规范 | 现状差异、项目规则、组件与布局骨架、代表场景及迁移清单 | 区分拟定规则、已接入实现与已验证范围 |
| 已有应用，需要审查 | 真实操作证据、问题清单、优化方案 | 仅对实际覆盖条件下结论 |
| 已授权优化实现 | 问题复现→设计→修订→原路径复验 | 逐项标记已验证与待验收 |
| 接续整改 | 读回 checklist、检查基线变化、处理剩余项 | 沿用旧证据，受影响项重新打开 |

小任务可用一份短 Markdown；复杂任务用[工作记录模板](../assets/review-workbook.md)的章节或拆分文件。删去不适用字段并说明理由，不为了填表扩张工作。

## 2. 从角色目标写连续故事

按[角色与行为覆盖](role-behavior-coverage.md)建立适度的连续故事与覆盖视图。应用场景补充真实入口、可见状态、反馈、键盘/焦点、内容与视口条件，分别执行下述功能、交互和视觉走查；不以静态矩阵代替实际操作。

## 3. 建立或沿用项目交互基线

先检查现有术语、导航、设计系统、组件库与交互约定，识别实际重复问题。成熟项目补齐缺口；新项目从代表故事建立最小基线。局部修复只更新受影响规则，不要求重建设计系统。

建立规范或涉及多个页面/共用模式时，读[项目交互规范与基础框架](../references/interaction-system.md)，使用[规范模板](../assets/interaction-spec.md)维护唯一入口，沿用项目已有文件位置。至少让本轮涉及的导航/对象定位、布局与信息层级、常见任务模式、组件状态、反馈/恢复、输入方式有明确约定，并链接代码与验证示例。

每个有争议的决定说明“角色目标→观察/假设→候选与代价→选择理由→可观察验收”。查证应针对具体不确定性，优先适用的平台规范、成熟模式及用户证据；书单、名气和个人审美不能代替依据。按需读[设计资料与应用索引](../references/design-reading-notes.md)，不要求每次任务研究全部书籍。

进入/退出专注、全屏、展开/收起等成对模式动作，默认使用同一控件、同一工具条槽位和锚定方位切换；用状态、图标及可访问名称表达反向动作，不能进入后把退出搬到另一角落。同一工具条的图标、尺寸和状态表达沿用同一视觉语法。涉及这些模式时，按[项目交互规范与基础框架](../references/interaction-system.md#模式切换的位置与控件一致性)检查普通/进入/退出、窄屏、嵌入与键盘路径；平台限制形成例外时记录依据和可找回出口。

共用行为通过现有组件、布局模板、语义样式变量和代表页面承接。已授权实现时落到当前技术栈；设计阶段明确待实现。统一同类行为并记录有依据的变体；不以统一为由抹平角色、数据密度或平台差异，也不为套规范替换整个框架。

界面开发前先读项目组件规范、目录与用法，按奥卡姆剃刀原则“如无必要，勿增实体”：优先复用、组合或合理扩展约定组件，避免反复新建同类型组件。没有约定时建立适度的项目公共库，避免每个需求各搭一套；共性与边界由实际场景确定，不预建万能抽象。功能、性能及兼容性满足场景时，可选用当前技术栈的成熟三方组件库，评估真实构建与运行成本。选型与新增判断见[项目交互规范与基础框架](../references/interaction-system.md)。

开发同时考虑性能。涉及新功能、重要交互、数据规模或共用组件变化时，读[场景性能约束与测试](../references/performance-guidance.md)：先查现有基线和约定，向用户核对尚未知的设备、网络、内容量、并发/峰值、等待容忍度与部署资源，再结合业内参考提出有依据的性能建议。覆盖界面加载、操作响应、持续流畅性、服务稳定性与抗压能力，建立适度的测量、回归与监测机制；建议值、已确认约定和实测结果分别记录。缺少信息时保留可修订的假设并继续独立工作，不把参考数字当作已获用户确认的验收线。

### 设计意图与实现一致性

已授权实现界面方案时，先辨明验收基准：用户明确采用的方案、项目规范和仍待选择的候选分别记录，不能把生成图自动视为批准，也不能在实现时悄悄放弃已约定的设计。有图稿时将其关键意图转为可观察的实现要求；无图稿时以项目规则与文字/组件方案为基准，不强行补图。记录可直接沿用项目现有清单，不要求另建文档。

有采用稿的改动，按本轮关键设计项维护“采用稿/规则→实现规格→运行截图/实际状态”的逐项对照，沿用项目清单或[工作记录模板](../assets/review-workbook.md#设计保真对照适用时)。例如卡片归组、主辅层级、间距和收纳关系被删减或替换时，记录约束、替代方案与保留原目标的理由；粒度以影响用户理解和操作的关系为准，不要求逐像素登记。

验收关注影响用户理解与操作的设计关系，包括信息层级、布局与空间、视觉语言和关键状态；具体维度及精度由本轮目标决定。库组件只是实现手段，使用了统一主题不等于实现了页面设计。遇到技术、响应式、权限或内容约束导致的实质偏离，记录依据、替代方式及原目标是否保持；不要求为每个像素或正常平台适配写理由。用户明确要求的设计发生冲突时先解决冲突，不能以个人偏好或省事为由降低标准。

用户提供表现参考时，记录影响理解的尺度、分区、对齐、留白与图文关系；只复制内容或恢复部分样式不等于保留设计。若当前任务只是交付方案，应选合适的文档、画布或支持的插件承载，不擅自改造整个应用，也不把概念图当作已经实现的界面。具体品牌资产与风格偏好留在对应项目，不成为其它应用的默认规范。

## 4. 用同一故事做三类走查

先走通主故事建立基线，再按发现和依赖迭代。发现问题立即记入清单，不等整轮结束凭记忆补写。具体检查按需读[三类走查指南](../references/walkthrough-guide.md)。

| 走查 | 核心判断 | 适用证据 |
| --- | --- | --- |
| 功能 | 正确的人对正确对象/版本做了正确的事，结果和来源能承接 | 真实操作、状态/数据、协议或测试；标明替身 |
| 交互 | 用户能理解现状，沿合理动线省力地找到动作、得到反馈、处理错误并继续任务 | 连续 UI 操作、往返/切换观察、键盘/焦点、恢复路径，必要时录屏 |
| 视觉 | 信息归组和主次是否符合任务，有无堆砌/冗余，核心信息视图占比与空间分配是否合理，收纳及变化状态是否易懂易用 | 同一故事下整页与组件多状态截图、实际展开/收起/操作及空间对照 |

视觉走查还应核对实现是否保留了上述设计意图。用可比较的角色、内容、状态与视口，将实际运行画面与采用方案对照；条件无法一致时说明差异及能作出的判断。功能正确、交互顺畅、视觉符合方案分别给结论；按钮可用、无溢出、构建或静态审计通过都不能代替视觉验收。实质偏差未解决或依据不足时，相应项保持未通过/待验，不用好看的设计图代替运行证据。

视觉走查同时评价易用性、阅读与操作动线。逐区说明“为什么此时要显示、与什么放一起、占多少空间、何时收起、如何找回”；不能只检查不溢出、点得到或风格一致。将归组混乱、重复信息、辅助面板挤压主视图、低频控件长期占位、收纳后难找回等问题分别写入 checklist，按用户后果排序。

用户工作界面默认不附带装饰性副标题、功能介绍、欢迎语和大段使用说明。逐句检查是否提供当前任务必需的信息；重复标题/按钮含义、泛泛介绍用途、没有新增判断价值的文字直接删除。普通操作应由清楚的命名、分组、控件和反馈表达；先修正这些结构，再判断是否仍需简短帮助。必要的条件、操作后果、输入要求与错误恢复提示就近保留；设计理由与实现说明留在工作文档。具体删减方法见[布局与文案决策](../references/progressive-disclosure-layout.md)。

不要用源码里“有按钮”替代入口可发现性；不要用 DOM 存在替代视觉检查；不要用美观截图替代完整交互。

多人场景用独立登录身份/会话检查权限和共享状态。在一个页面切换角色标签只能验证该页面模拟。浏览器改视口只能支持该视口的结论，不能替代手机硬件、软键盘或真实网络环境。

证据注明来源类别：真实运行、自动测试、协议仿真/fixture、静态分析、设计推演、用户反馈。用户报告可作为问题线索，复现前保持“待查”；不要把模型扮演用户称为真人可用性测试。

若有 AI 输出，分别验收应用承接与模型语义质量。假回复可测加载/失败/展示；真实理解须对真实调用核验事实、否定、条件、数字、责任与来源。不要因接入本 Skill 就更换模型或重构其工作流。

## 5. 在共用记录中补充应用证据

状态、稳定 ID、证据复用和失败重开由[共用审读与修订规则](../references/common-review.md)维护。每项补充故事/步骤、适用规则/组件、实际运行条件及功能/交互/视觉结论。沿用[应用记录视图](../assets/review-workbook.md)，混合任务引用同一问题 ID，不另建第二套清单。同根因修复仍须复验各受影响故事；桌面通过不能掩盖移动端未验。

## 6. 设计改进与 imagegen

先解释问题如何妨碍用户目标，再提出最小充分改动。检查共用组件/状态逻辑能否修正根因。按统一入口区分必须满足的业务条件、当前实现限制和可重新选择的历史设计。常规修订沿用有效规范；明确重设计时按方案模块论证替代与迁移，不默认继承导航和结构，也不无依据推翻有效设计。

涉及布局、收纳或复杂选择时，读[渐进式展示与布局决策](../references/progressive-disclosure-layout.md)。先确定此刻必要内容、辅助内容和必须同时对照的依据，再选呈现方式。渐进式展示用于按需补充；分步流程须有任务顺序依据。用明确标签、摘要和状态提示保证收纳可发现；关键条件不能因低频而消失。优先减少猜测、记忆和往返，不以固定点击数、固定主视图比例或“藏得更多”定义简洁。

预先视觉设计是界面实现的重要准备。在条件允许、能帮助判断方案时，尽量先使用 imagegen 或具备相近视觉探索能力的工具形成可查看的候选，再决定实现；尤其适用于新页面、较大布局或视觉调整，以及信息层级、空间关系和多状态交互。不要等控件拼完才补图，也不要只凭技术可用性决定最终外观。用户明确要求 imagegen 时执行生成，并遵循其技能与可用接口；其他环境可使用合适的近似能力，不绑定某一供应商。

这一偏好按决策价值适用，不要求每次改文案、简单局部样式修订都生成图片。已有明确采用且仍适用的设计稿时优先沿用；工具不可用、素材受限或生成对当前决策无帮助时，记录原因并采用合适的文字、组件规格或可查看原型继续，不阻塞已授权工作。预先视觉方案用于比较和确定意图，不能代替真实实现与运行验收。读[Imagegen 设计闭环](../references/imagegen-design.md)，使用所在环境可用的图像生成能力及其技能约定。

按待说明的问题选择图的粒度，不限定为一张完整大界面图。可追加控件或组件细节图，展示默认/收纳/展开、选中/编辑、加载/结果等相关变化态；必要时用连续状态图标明触发动作和返回路径。整页图用于判断主视图占比与空间关系，局部图用于讲清分组、收纳入口、状态变化和操作细节。只生成对本轮决策有帮助的图。

生成前将 checklist ID、适用规则/组件、角色、当前状态、关键正文、允许变化与必须保留的结构写入提示词。已有界面时先看截图，适合时作为参考；没有界面时明确为新设计。生成后实际检查图片，记录采用/舍弃原因并映射到实现规格；图片不能自行改写交互规范。

设计图标注“设计提案/示例数据”，与 before/after 运行截图分开。图中的文字、权限、状态与控件不自动成为产品事实；示意排版须转成实际组件与交互，不能整张图铺作可操作页面。

工具不可用时保留设计说明、提示词及“未生成”状态，继续可执行的走查修订；文字提示词不能冒充已生成图。运行环境不可访问时交付候选方案与待执行验收，不宣称已完成视觉复验。

## 7. 逐项实现、复验、交接

有实现授权就按依赖与优先级逐项推进；仅审查任务交付问题和候选方案。不要增加每个小修订都要审批的流程，也不要把审查授权解释为发布/对外发消息授权。

每项循环：确认基线与复现→记录验收标准→设计/修复→运行与影响范围相称的检查→按原角色、原数据和原路径复验→即时更新 checklist。测试数据写入隔离环境；读回运行实例版本，避免验收旧页面或误写真实业务记录。

局部测试后，走完受影响的连续故事，确认修复没有把问题移到下一步或另一角色。视觉改动对照实际渲染中的归组、冗余、主视图占比及收纳前后空间，并操作展开→使用→收起→再次找回的路径；交互改动操作真实控件；共享状态检查另一身份；模型质量用对应证据。未变化且仍适用的历史验证可引用，不重复消耗。

功能与关键流程相对稳定、数据和部署形态具备代表性时，主动向用户建议一次范围明确的性能及负载/压力测试，说明场景、目标负载、持续时间、成本与停止条件。日常性能基线及受影响回归随开发开展，不等成熟后才关注；已授权测试就执行并记录结果，未授权或环境不具备时保持具体计划与待验项。测试机制可建立在隔离环境中，高负载作用于共享/生产环境或付费依赖前须有相应授权。

结束前对账故事覆盖与 checklist：

- 每个本轮必验结果是否有证据，所有新发现是否入账？
- “已验证”是否对应当前实现和实际环境？相关旧证据是否仍有效？
- 未完成项是否有原因、影响、依赖、下一步和恢复条件？
- 设计取舍、实现范围、用户说明与交接是否一致？
- 共用规则、组件实现与代表页面是否同步？例外和待迁移页面是否仍可追踪？
- 任务、评审、需求及主体说明是否已按真实读者角色完成不跳页、不点外链的复读，必要背景与逻辑是否在正文齐备？
- 是否复用了适用组件？新增组件/依赖是否有必要性及成本依据？性能约定、基线、受影响回归及成熟阶段测试建议是否落实或明确待办？

交付简短结论：完成了哪些用户任务、主要改动、证据入口、未完成项和下一步。交接文件开头放当前基线、最近有效结论、剩余 ID 和最先应做的操作；历史记录留在后面，避免下一会话重新走完整套。
