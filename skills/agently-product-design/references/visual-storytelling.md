# 视觉叙事与载体选择

适用于品牌主张、方案演示、图文说明，以及把已有聊天或演示保存成项目资料。目标是让内容的意义、阅读次序与视觉表现一同保留。用户认可的参考优先；下列风格来自用户提供的参考，是可选择的表达语汇，不是通用审美结论，也不把示例措辞转为已批准主张。

## 概念插图的可选辅助

关系、概念、产品理念或功能价值适合用少量抽象界面元素表达时，按[Spotkit 辅助表达](concept-illustrations.md)判断是否使用已安装的 `spotkit`。它维护该类插图的几何与同族一致性；架构、业务流程、证据与边界仍按本包的专业指导，不用隐喻替代精确信息。

## 从参考提取表达关系

先区分“忠实整理/迁移”与“基于材料提出新方案”。前者只使用取得的来源内容及明确决定，不混入外部背景或作者新增判断；缺少原文的部分标明缺失，不为凑齐结构补写。建议仍保留建议的性质，认可视觉风格不等于批准其中全部内容。若另提建议，须符合授权并单列，不能静默替换原方案。保留视觉效果也不能擅自改写内容；原图直接作为档案时注明内部文字不可单独编辑。

先记录读者第一眼应该看什么、接着理解什么：主张和解释的比例，字标与中英文的层级，图标与条目的对应，背景如何分组，箭头表示什么，留白怎样组织节奏。内容、版式和语气分别核对。参考缺失时说明不能逐项还原，可以按已确认目标提出新候选，不能声称复刻原稿。

保存或迁移时保留原生标题、加粗、引文、图表、图像与必要分区。转换器不能仅为方便而删除强调格式或把图降为一句“见附件”。正文前部先让读者理解对象、主张及必要条件；研究过程和详细备查资料后置。候选状态保持可见，但不以反复免责声明淹没主张。

## 高密度信息的视觉注意力策略

适用于所有面向人的图文表达，尤其是密集流程、信息模型和比较视图。先确定“第一眼的主结论／路径 → 就近的条件与异常 → 按需展开的依据”，再设计视觉。信息多不等于每项都要同时争夺注意力。

- **让图形承担信息。** 用位置和连接表达顺序、包含与依赖，用统一图标识别角色／对象，用状态色块配文字识别等待、风险和完成。可用计数、长度和分组替代重复段落；面积、长度若编码数量，应保持对应尺度，不能用装饰制造虚假比例。
- **建立少量层级。** 主路径用尺度、字重或对比突出，配套条件紧邻对应节点，参考说明减弱但保持可读。中性表面为主，强调色留给实际焦点；不要把每个段落都包成同样大小、同样饱和的卡片。先合并重复和重组关系，不靠缩字号、铺色或添加图标掩盖拥挤。
- **多层文字要有可感知的视觉差。** 先标定各层的作用，例如“阶段标题／辅助过程／准入判断／失败去向”，再按下方规则选用字号、字重、明度、位置或线型。简单局部重点可以只靠字重表达；层次仍不清楚时才组合其他手段，不要求每个重点同时放大、加粗、着色和加框。主标题形成入口；决定能否继续的条件集中、明确；异常有独立标记和去向，不能作为浅灰脚注隐没。辅助说明降低视觉重量，但保持可读。跨列相同层级使用同一规则，实际成品决定差异是否足够。
- **鼓励成熟图标库。** 没有既定体系时可优先使用 Font Awesome；已有体系时优先复用，避免为少量图标混入另一套语法。选语义匹配、同一家族／风格与视觉尺寸的图标，不把品牌标识当通用角色图标。关键图标配短标签，装饰图标不重复朗读；独立图标按钮有可访问名称和明确状态。图标不是每句话都要有的装饰。
- **按载体提供资源。** 确认所选图标在实际版本和许可中可用，不假定 Pro 资源免费。优先复用已安装依赖，按需引入；独立文档可内嵌 SVG 子集并保留要求的归属／许可，减少字体、CDN和网络失效风险。资源加载失败时文字和主关系仍可理解。SVG、字体或组件由目标载体支持情况决定，不强制某一种技术。
- **保留判断所需信息。** 数量、责任、准入、失败去向和重要限制默认可见；字段明细、逐项计算和长依据可在原位展开，摘要明确里面是什么。颜色同时有标签、形状或线型编码，不能仅凭色相区分。手绘风格可用于标题和边界，不牺牲正文精确性。
- **按注意力顺序复验。** 打开实际阅读尺寸，记录最先突出的对象是否符合主任务、条件是否邻近、读者能否沿关系完成理解，再验证真实交付中已有的必要交互。主题、视口、背景和导出检查须符合[验收范围](common-review.md#文档制品与产品界面的验收范围)的触发条件，不把这些维度列为文档默认矩阵。文档图解只维护一套字号方案，不为走查另造大小字号模式；宿主缩放不得禁用。应用按[显示约定](interaction-system.md#显示约定统一排版与柔和灰阶)处理阅读字号与缩放，不另造例行多档测试。检查图标缺失、歧义、对比和失去颜色后的含义。静态角色走查不冒称眼动或真人理解测试；用户反馈推翻旧结论时重开原问题。

多层文字专项复验：先暂不逐字读正文，检查能否通过版式识别“在哪一阶段、哪项是卡控、哪里是失败处理”；再逐字核对内容与视觉强度是否一致。用实际阅读宽度复验，不能以放大的局部截图证明整页层级明显。记录观察和修订，不把作者熟悉内容当作新读者能辨认的证据。

方法依据：[NN/g 视觉层级](https://www.nngroup.com/articles/visual-hierarchy-ux-definition/)与[视觉设计原则](https://www.nngroup.com/articles/principles-visual-design/)提供尺度、对比和分组的判断框架；[Font Awesome SVG sprites](https://docs.fontawesome.com/web/add-icons/svg-sprites/)说明无需运行时 JavaScript 的 SVG 使用方式。它们支持选型与审读，不证明某一版图已经降低阅读负担。

### 图中文字与视觉强调的选用

先按目标读者明确本图的问题、第一眼要看到的结论或路径、随后需要的依据，再选择表达方式。每项强调都应能说明帮助读者找到什么；阅读层级与局部重点分别处理，同级节点的名称保持一致，当前需要关注的内容可在该层内突出。

| 表达需要 | 优先考虑的手段 | 使用要点 |
| --- | --- | --- |
| 区分标题、节点名称与说明 | 少量字号层级、字重及间距 | 节点名称可用中等或半粗字重，解释用常规字重；标题无需重复正文，长说明不整段加粗 |
| 突出局部关键动作、条件或数值 | 同字号下局部半粗／粗体 | 强调能独立理解的短语；条件、否定、单位和比较对象保持紧邻，不只突出有利数字或截断限定条件 |
| 表达归属、顺序或并列比较 | 邻近、对齐、留白、轻底分区 | 先安排位置再加装饰；多行说明通常左对齐，短节点标签可居中，数值按比较需要对齐 |
| 区分主链路与反馈、可选等关系 | 布局、连线粗细、线型、箭头与标签 | 主链路连续可追踪；次要路径仍可读且去向明确，同一线型不混用含义；已有流量等定量线宽编码时，不再用线宽暗示重要性 |
| 标出焦点、系列或状态 | 少量强调色配直接标签或符号 | 中性色承托内容，颜色含义稳定；不把每个节点染成不同颜色，也不让同一种颜色同时表示类别和冲突的状态 |
| 解释变化、异常或证据 | 对象旁的短注释、必要的引线或范围标记 | 标注靠近所解释的对象，避开数据和连接线；能直接标名时减少往返查图例，保留必要单位与条件 |

字重通常从“常规＋一种重点字重”开始，按实际层级增减；例如支持相应字重的字体可用 400 与 600 或 700，这只是实现参考，不是强制数值。优先沿用项目字体，并确认实际字体、中文回退和交付格式能呈现粗细差异。不能只看到代码写了 `font-weight` 就认为强调生效；也不用极细、过浅的小字来衬托粗体。加粗后重新看换行、行高和文本框边界，避免字宽变化造成遮挡或挤压。工具不支持局部字重时，可用位置、间距或可读的对比补足。

数量关系继续使用正确的刻度、长度或位置表达；不要为突出重点而放大条形、气泡或节点到让读者误认数量变化。重点太多时先重组或精简，不继续叠加粗体、颜色和边框。

验收分两遍：先在实际阅读尺寸快速扫视，记录首先注意到的内容是否符合读者任务、同级标签是否一致、是否所有文字都在抢重点；再逐字检查重点与其条件是否一起可见，次要文字是否仍可读，字重是否真正生效。导出属于交付范围时也核对导出结果。沿原问题记录观察、修订和复验，不用“已加粗”代替层级判断。

2026-11-13 核对：[Datawrapper 字体指导](https://www.datawrapper.de/blog/fonts-for-data-visualization)支持将粗体用于标题和少量重点、长说明保留常规字重；[图表文字指导](https://www.datawrapper.de/blog/text-in-data-visualizations)支持就近标注、有限文字层级和有目的的强调。上表将这些方法与 NN/g 的尺度、对比和分组原则用于本包图解场景，具体字重与组合是选用建议，不是统一模板。

## 可组合的参考风格

本节是可选案例库，只在参考、受众与交付目标适用时采用；不属于所有文档的默认版式或完成门槛。颜色、字号、圆角、图标与具体措辞由当前项目和参考决定，不继承某个历史任务的品牌资产。

### 主张卡

适合凝聚一个品牌核心或方案结论。可采用深墨色面、浅色正文及一处克制的品牌强调色；小号主题标识、醒目字标、主张、中文解释、补充叙事依次排列。细分隔线连接上下两层信息，尾句可以承接情绪。重点是主张与解释的层级，不能将所有文字同等放大或把整篇文档铺成深色卡片。深色是局部表达选择，不自动改变产品主题。

### 聚焦字标

适合开场、收束或一句话定位。居中或沿统一轴线排列字标、短英文 Slogan 与中文品类说明，让三者有清楚的尺度差；保留有用途的留白。不能用超大空白挤走需要同时阅读的解释；正式 Logo 使用已授权标准资源，不用近似字体冒充母稿。

### 图标条目

适合比较官网、欢迎页、传播视频等使用场景。每条用同一尺寸的线性图标及轻底容器，旁边依次放场景名、示例表达与作用说明，条目间用间距或细线划分。图标辅助识别，文字仍完整；不混用多套图标语法，也不把每条都包成厚重大卡片。无可用图标库时可用统一的简单矢量图，不用随机 emoji 代替专业图标。

### 机制对照图

适合说明旧方式与目标方式的关系变化。左右采用同一问题、对象粒度与尺度：一侧展示顺序交接，另一侧展示共同上下文、双向反馈与共同成果。用箭头、标签和空间位置解释机制；一侧用中性浅底，另一侧可加轻微强调底色。保留两侧适用范围与方案性质，不能将示意模型扩大为所有竞品的事实，也不能靠强弱配色制造没有依据的优劣。

### 前后结构对照

适合解释改造前后谁负责什么、哪些对象合并或保留、哪些关系改变。前后采用相同的阅读方向与对象粒度，重复角色和接口沿同一列对齐；有足够宽度时可左右并列，纵向阅读面可上下排列。用轻底分区表达系统或职责归属，组内白底节点承载名称与一句必要职责说明，连接线标出真实流向。中性色保留共同背景，少量强调色突出本轮变化；迁移中的对象可用虚线配状态文字，但不把虚线同时当作异步或可选关系。新旧名称可映射，不能为了对齐而假装新方案仍保留已取消的实体。

### 流程与时间轴结合

适合同时解释“过程怎样发生”和“读者何时看到结果”。先用对齐的流程行展示不同方案的步骤、依赖与并行，再在相邻区域用同一起点和刻度的时间轴表达可观察状态及关键时刻。步骤示意明确是否按时间比例绘制，不能让等宽步骤暗示等长耗时；时间轴中的长度则对应持续时间。按实际依赖画清流式、重叠或等待阶段，不能把空间上并排误画成串行。必要条件放在对应步骤附近，测量环境与方法放在图末简短说明；只有过程资料而没有测量记录时只画过程，不补造时间和性能收益。

### 同条件指标比较

适合比较多个对象在相同条件下的耗时或其他定量指标。按场景分组，每个对象的两组数值相邻排列，共用单位、零点和刻度，数值就近标出；环境不同时分面呈现并明确条件。各分面若使用不同量程，应显著标明，不能跨面凭条形长短比较。中性灰与一个强调色区分系列，图例和文字名称仍保留。已有多次测量时，可用条形表达明确命名的统计量（如中位数）、点表达单次样本，说明样本数与统计口径；只有汇总值就不生成样本点。比例标签根据原值计算并标明方向，例如耗时比为“旧耗时／新耗时”，避免含糊的“快若干倍”。

以上三类提炼自用户于 2026-11-10 提供的结构对照、流程与时间轴、性能比较截图。共同视觉选择是浅中性分区、规整对齐、轻边框、清楚的文字层级和少量强调色；项目主题需要时可调整，重点保留关系与比较方式。标题说明读者要理解的问题或已有依据的结论，副标题只补充必要条件，不固定添加介绍段。截图中的产品名称、测试数据和效果不作为其他项目的事实或默认参数。

这些风格可以与少量短表、正文解释组合。先选能表达本次问题的模块，不要求全部出现，不把所有方案做成相同模板。会话内使用时仍按下方宿主能力直接呈现，不因选择上述版式改成交付独立网页链接。

## 先选表达 再选工具

先确定读者最后在哪里使用内容，以及要做什么：当场阅读、回答一个问题、共同修改、长期归档，还是在浏览器中操作。用户指定了平台、已有文档或交付格式，就在那里完成。未指定时，选择能满足这些动作、切换最少的方式。目标平台由读者的工作决定，不一定是 Agent 所在的会话。区分图的制作方式与整篇文档的交付方式；需要一张图不等于需要一个网页。

- **当场阅读或决定。** 短文、走查记录和比较结果直接在会话内用段落、列表或表格呈现。确有待用户回答的问题且当前客户端提供原生提问控件时，用控件收集选择或短答；没有控件时直接用文字问。不要把已经完成的结论做成需要用户填写的表单。[Codex App Server 的用户输入协议](https://learn.chatgpt.com/docs/app-server#toolrequestuserinput)描述了客户端接收问题、返回回答的机制，具体入口以当前会话为准。
- **在会话内看趋势、关系或结构。** 优先发现并使用当前宿主支持的内嵌图表、结构图或可视化能力。Codex 环境若提供官方 `visualize` Skill，按其当前输出方式和图表规范呈现，正文在图前后就近说明判断。不要用提问表单代替图表，也不要因为普通文字能描述图中信息，就取消有助于比较或理解的图形。
- **区分呈现位置与实现技术。** 宿主内嵌可视化也可能需要生成 HTML/CSS/SVG 片段或本地文件；这些是客户端呈现回复所需的实现，不能因此判为独立网页。判断依据是读者能否在会话中直接看见和使用内容。宿主要求的片段及内容引用按对应 Skill 执行，不改成交付本地网页链接、要求另开浏览器或启动临时站点。没有内嵌能力时，再选择受支持的图片或附件，并说明实际交付方式。不能仅凭截图断言它来自哪个工具。
- **保持图型规则的适用范围。** 技术架构的 SVG 默认要求只用于技术架构梳理；阶段关系、叙事节奏、比较图、普通流程或曲线不因存在节点、连线而套用该规则。一般会话图形按宿主能力及当前有效约定选择。
- **持续编辑、评审或归档。** 优先沿用目标项目中已有的可编辑正文。Claude Code 若提供文档制品且这是预期归属，可用其承接后续编辑；桌面端可以在侧栏阅读，终端可返回文档链接，具体取决于客户端和账号能力，见 [Claude Docs 官方说明](https://support.claude.com/en/articles/16923645-get-started-with-claude-docs)。若源稿由代码仓库维护，就修改仓库中的源文件，不另建一份云端正文。
- **在项目中共同维护图文。** 在 RioWork 中，供成员检索、引用和修改的说明放在项目文档，需移动节点、调整关系的图用原生画板。正文在对应位置解释图的结论，按实际能力嵌入或关联画板。确认目标目录和读写权限，保存后重开检查正文和可编辑元素。其他平台也按同样的阅读与协作需要选型。
- **独立网页有明确用途时再做。** 用户指定浏览器或 HTML 交付，或必要的交互、排版、离线分发在原生载体中无法实现时，可交付 HTML/CSS，并在预期环境打开验证。原生能力不足时，先看现有文件、嵌入图或附件能否补足；若改换载体会丢失必要的编辑、访问或反馈能力，说明取舍。能写 HTML、希望更美观或只是临时展示，都不足以单独决定交付方式。

| 交付需要 | 优先考虑 | 需要实际核验 |
| --- | --- | --- |
| 会话内比较、理解或探索 | 宿主内嵌图表或可视化能力 | 图直接出现在回复中，文字解释相邻；按宿主指导验证绘图和适用交互 |
| 持续阅读、检索、批注 | 原生文档与原生图文块 | 强调、图像、段落和引用保存后仍正确 |
| 技术架构梳理，未另指定视图 | 按[架构图规则](diagram-and-board.md#架构与流程图的默认表达)直接绘制 SVG 逻辑分层图 | 层间支撑、边界、实际 SVG 渲染与源文件，不用 Mermaid 替代 |
| 关系图、版式讨论、逐项移动和修改 | 原生画布或兼容可编辑画板 | 元素与资源完整，文字和关系可编辑，重开一致 |
| 精确排版或可调参数的解释 | 宿主内可用的图形或交互可视化；需要独立网页时再用 HTML | 实际交付的预览／嵌入效果；约定导出时检查导出；脚本与资源限制 |
| 分页演示或外部分发 | 可用的演示、文档或 PDF 插件 | 源文件与最终阅读/播放版本一致 |
| 图片探索或位图素材 | 可用的 imagegen | 文字与语义准确；位图内部不可独立编辑的边界 |

先发现当前已连接工具和目标载体能力，能完成时直接用；不足时再发现合适插件，实际调用前读取其技能与合同。用户未要求安装或授权新服务时，不为追求工具数量擅自连接账号。工具可用不等于嵌入可用；文件上传成功也不等于当前页已显示。

原生文档不能承载目标版式时，优先在同一项目保存可编辑画布或适当成品，并在正文相关位置提供受支持的预览与简短解释。尽量让读者当页理解；确有嵌入能力缺口须说明，不能只给裸链接并称为已保留展示效果。不为复刻一张品牌卡而擅自重做整个阅读器。

## 会话内图形表达的选用

当读者需要同时理解多个对象的归属、层级、连接、先后、分支或比较关系，连续文字会迫使他记住多处信息再自行拼装时，主动考虑在回复中配一张结构清楚的图，不必等用户指定画图。先确定图要帮助读者回答哪个问题；简单事实、一条动作或本就清楚的短文仍直接用文字，不为统一风格强行配图。

| 读者要理解什么 | 图形怎样承担信息 |
| --- | --- |
| 哪些对象属于同一部分，整体由什么组成 | 用有名称的分区和层级表达包含关系，必要的属性放在对应对象内 |
| 对象如何连接、依赖或交换信息 | 用连接线表达真实关系，方向、输入输出或连接条件就近标注，区分连接与包含 |
| 谁先做、谁接手、何时分支或返回 | 用流程或泳道表达角色和动作，突出主链路，给反馈路径预留空间；并行、汇合和条件分别画清 |
| 多个阶段、选项或指标有什么差异 | 用对齐的阶段结构、并列比较或合适的统计图，保持同一比较口径；只有数值才使用定量尺度 |

**先组织关系，再选实现。** 在当前宿主支持会话内嵌图形时，优先直接呈现。可按内容采用 SVG 绘图，或由 HTML/CSS 排列分组与文字、SVG 绘制连接；实现服从语义和宿主约定，不固定为某种模板、网络图、三维造型或一排卡片。需要精确连接与密集文字时，平面结构往往更直接。读取宿主实际提供的绘图技能并使用其输出方式，不自行复制一套可能过期的客户端协议。技术架构的专项规则仍按画板指导执行。

**让图和正文各尽其责。** 图内保留对象名称、必要属性、分组、连线含义及判断条件；前后正文解释结论、取舍或尚未确定的事实。不要把整篇分析塞进图里，也不能只画空框，让读者到正文中逐项找出每条线是什么意思。相同层级采用一致的表示方式；主要路径与反馈等次要路径可辨，线从正确对象出发并到达正确对象。未知关系保持未定，不为版式整齐补造流程或权限。

**按读者看到的结果验收。** 真实生成后打开宿主预览或实际阅读面，逐项核对分组与归属、连线起止与含义、条件与分支、文字可读性。分支缺失、线穿过文字、分组造成错误归属或需要靠颜色猜意义，都先修正再复验。随容器调整布局时保持关系和阅读顺序，不能只缩小整图。最终回复必须包含宿主支持的内嵌引用或图形内容，不能只留下独立网页链接。生成文件、预览渲染、最终回复引用与用户客户端实际显示分别记录，不将其中一项当成全部完成。

## 内容与视觉各自验收

- 对照参考逐模块记录保留、调整、缺失及原因；内容状态、主张强度和视觉关系分别检查。
- 在实际目标载体打开，判断主张是否先被看到、解释是否相邻、字重尺度与留白是否形成节奏、线条和图标是否统一、对照图是否可读。不能以“用了画布”“已加粗”“已截图”代替判断。
- 检查真实正文在实际交付容器中的可读性。仅当[验收范围](common-review.md#文档制品与产品界面的验收范围)规定的触发条件成立时，补充相应窄容器、主题、背景或导出检查；一次性报告不默认检查手机和深浅主题。文档内嵌制品及其预览保持一套字号方案，不额外制作大／小／普通版本；标题、正文、标注仍有层级。固定尺寸图板可采用局部阅读或分页，不假报自动响应式；不缩小正文掩盖拥挤。
- 保存后重开，检查内容与资源，交付约定包含编辑或导出时再检查相应能力；再按未参与会话的读者复述对象、依据、结论、未定条件和下一步。文字通过、视觉通过与真人理解分别下结论。

依据：[NN/g 视觉设计原则](https://www.nngroup.com/articles/principles-visual-design/)支持尺度、层级、对比、平衡与邻近的判断方法；具体风格来自用户参考，并非该来源规定的模板。没有实测证据时，不宣称这些风格必然提高转化或理解率。
