# 项目交互规范与基础框架

建立项目范围内可复用、可检查的交互约定，使新增页面能沿用已有行为，改进能进入共用实现。以下工作方法是本 Skill 的综合应用方案；它不指定技术栈、品牌风格或固定页面结构。

## 1. 先建立最小基线

盘点实际存在的导航、页面类型、同义术语、共用组件、设计变量、状态处理和可访问性约定。找出“同一动作行为不同”“同一状态文案不同”“页面重复实现同一控件”的证据。已有规范与代码冲突时记录差异，不默认任一方正确。

用一个主故事和关键变体确定首批规则。例如列表找对象→读详情→编辑→保存→返回，可暴露对象定位、筛选保留、表单、异步反馈和返回规则。没有项目证据时先记为候选，避免为未来想象的页面建立庞大库。

在项目已有文档入口维护[交互规范模板](../assets/interaction-spec.md)。同一份规范链接实现、示例和验收记录；走查 checklist 管整改状态，不复制一份规则正文。项目很小时合并为几个章节即可。

## 2. 用四层约定承接设计

| 层次 | 需要统一什么 | 可落到哪里 | 验收方法 |
| --- | --- | --- | --- |
| 产品与任务 | 对象名称、用户目标、状态含义、角色边界、信息架构 | 术语表、对象/任务关系、导航与返回约定 | 用户能定位当前对象，跨页术语和操作效力一致 |
| 任务模式与布局 | 列表找对象、详情处理、编辑保存等模式；主内容、依据、动作的位置关系 | 现有页面模板、工作区布局、模式文档 | 代表故事用实际内容走通，检查展开与窄屏 |
| 组件行为 | 输入/输出、启用条件、触发、反馈、焦点、退出与恢复 | 共用组件或行为模块、状态示例 | 真实操作状态转换，检查组件组合后的表现 |
| 视觉基础 | 有语义的字体、色彩、间距、密度、层级与动效约定 | 当前样式变量/设计 token、主题与基础样式 | 语义用途一致，长内容、缩放与输入目标可用 |

设计 token 是可复用的命名样式值，例如“正文文字色”“控件间距”，不是新增一套任意数字。先复用项目值，再根据内容和任务补齐缺口。颜色统一不能弥补保存、关闭、返回等行为不统一。

GOV.UK 将样式、组件与任务模式分别组织，并以适用性、一致性和验证范围评估新模式；可以借鉴这种组织方式，不能直接把政府办事流程移植到业务工作台。[设计系统](https://design-system.service.gov.uk/) · [贡献标准](https://design-system.service.gov.uk/community/contribution-criteria/)

## 3. 项目规则应回答的问题

只补齐本轮涉及的部分。每条规则记录稳定 ID、适用条件、依据、例外、实现位置和验收方式。

| 主题 | 必须作出的具体决定 |
| --- | --- |
| 信息架构与导航 | 页面按用户对象/任务还是其他经过验证的模型组织？全局导航、对象内导航、上下文动作分别在哪里？深链接/重开如何定位？返回列表是否保留筛选、选择和滚动？ |
| 布局与展示层级 | 当前核心任务是什么？哪些信息须共同可见？什么常驻、什么展开、什么随任务上下文出现？面板挤压还是覆盖内容，窄屏如何承接？ |
| 动作与文案 | 同一动词是否代表同一结果？跳转和命令能否区分？主要动作在各类任务中的位置、出现条件和不可用原因如何表达？ |
| 表单与编辑 | 显式保存还是自动保存？何时校验、错误如何定位？取消/返回/关闭分别影响什么？草稿、脏数据和保存失败如何处理？ |
| 查找与批量操作 | 搜索、筛选、排序范围是否可见？空数据和无匹配是否区分？选择是当前页还是全部结果？处理后如何显示部分成功？ |
| 异步与反馈 | 何时显示忙碌、结果、失败、等待他人？重复触发如何处理？后台任务在哪里找回？不可恢复错误如何承接下一步？ |
| 风险与恢复 | 哪些动作可撤销，哪些需解释后果或确认？按真实后果决定，不能给所有动作添加确认弹窗；关键依据靠近决定点。 |
| 输入与可访问性 | 键盘、触摸、屏幕阅读器的名称、顺序、焦点与替代操作如何工作？遵循平台原生行为，按需核对标准及例外。 |

权限、数据一致性与业务状态由真实业务逻辑保障；界面隐藏、按钮禁用和收纳不能替代它们。领域状态（如“待审核”）与界面状态（如“加载中”“已展开”）分开定义，避免用一套含混枚举同时表达。

将文案精简落实为共用约定：页面头部、卡片与面板默认只展示必要标题、内容和操作，不要求副标题/介绍字段，不生成泛化说明作为兜底；可选说明缺省时移除相应布局占位。说明必须有当前任务的信息增量，具体判断见[布局与文案决策](progressive-disclosure-layout.md)。规则、设计论证和开发注释不直接进入产品界面。

## 4. 模式选择与例外

遇到新场景先找现有模式，判断是否适用；再考虑有明确条件的变体；最后才新增模式。记录实际代价，例如切换造成的记忆负担、窄屏遮挡、重复操作次数及维护分叉。依据不足时选择可撤回的候选，安排最小验证，不把试验写成已证实规范。

详细的常驻/收纳/分步判断见[渐进式展示与布局决策](progressive-disclosure-layout.md)。同一动作应有稳定含义；不同平台可以用各自熟悉的呈现形式。新手需要解释、熟练用户需要效率时，优先保留一条清楚的基础路径并提供可发现的加速方式，不未经观察就制造两套应用。

外部依据按问题选：平台行为查对应平台官方指南；Web 组件语义与键盘行为查 [WAI-ARIA APG](https://www.w3.org/WAI/ARIA/apg/patterns/)；布局可以参考 [Carbon 的内容层级与布局指导](https://www.carbondesignsystem.com/building-blocks/foundations/2x-grid/guidelines)。仅采纳与当前内容、设备和任务相符的原则，不照抄列数、断点、侧栏或品牌样式。

### 模式切换的位置与控件一致性

将下列规则落实到已有组件与本轮验收，不为每个模式另造一套控制器：

- **成对动作同位切换。** 专注/全屏的进入与退出、展开与收起，默认由同一个可持续访问的控件完成。状态变化保持原工具条槽位、相邻顺序、点击区域和锚定方位；画布扩展至视口也不把退出改放另一角落。切换后更新图标、状态与下一动作提示，避免用户重新寻找出口。
- **跨宿主也由同一入口反向操作。** 工作区、iframe、嵌入编辑器或局部画布接管展示模式时，原控件仍能读到真实模式并请求退出，焦点与草稿保持。原位置已有可用退出时不重复叠加悬浮出口；模式恢复、页面切换或入口确实不可用时才提供清楚的恢复出口。快捷键是补充，不代替可发现的退出。
- **工具条使用同一视觉语法。** 同级操作采用一致的图标风格、尺寸、间距、命中区域及悬停/按下/禁用/焦点表达。图标工具条中的高频、可辨认操作可直接显示，附可访问名称和悬停/聚焦提示；有多种取值的图标仍打开选择菜单，不强改为二元开关。不为局部省事插入孤立文字入口或藏进含混总菜单。是否直接显示仍按用户目标、频率与可发现性判断，不能推成所有工具条都只准图标。
- **状态与下一动作分别表达。** 使用固定名称加按下状态的开关时，名称保持稳定并提供适合平台的状态语义；使用随状态变化的动作名称时，准确说明下一步。图标变化不能引起控件尺寸或邻项位置跳动，不能仅用颜色表示开关。
- **验收同位与可逆性。** 连续执行进入→退出→再次进入，用真实截图或布局量测比较同一容器中的槽位、锚定与相邻顺序；同时检查键盘焦点、菜单的Escape优先级、草稿、画布/编辑器实例是否保留。覆盖本轮涉及的宽窄、字号、嵌入/跨frame和宿主恢复；单看两个静态状态各自有按钮不算通过。

这是通用设计默认与用户明确要求的结合；平台系统控件强制位置、原入口随导航真实消失等例外，记录限制、恢复路径与验证，不用例外绕过本可实现的同位切换。[Apple全屏操作](https://support.apple.com/guide/mac-help/use-apps-in-full-screen-mchl9c21d2be/mac)提供同一窗口控件进入/退出的成熟实例；[WAI-ARIA按钮模式](https://www.w3.org/WAI/ARIA/apg/patterns/button/)支持开关状态、可访问名称与焦点要求，不将其解释为对所有产品位置的强制标准。

## 5. 将规范落成可用骨架

### 严格遵从：统一到页面组合，不止基础控件

实现任何新区域前，核对四层维护归属：基础控件/交互行为、页面族骨架/布局、语义表面与主题token、业务内容/状态。读取实际公共实现、允许变体和代表页面，不能把“用了同一组件库/颜色变量”当作全部统一。

同类内容必须沿用既有骨架、表面（画布/正文/目录辅助/浮层）、边界承担层、标题/正文级别、密度和响应式合同；业务组件只组合内容、状态和动作。新增局部容器、硬编码/重定义底色、边框、阴影、圆角、字号/间距或断点前，先判断是否重复了公共owner；如是，应复用或在公共owner扩展。页面自身可以表达真实业务布局，但不能另立同用途的视觉规则。

允许有依据的页面族/任务差异，不将所有页面强制为同一模板。例外必须说明具体业务或容器约束及受影响条件，不能由Agent以省事/个人审美自行降级已统一规范。验收必须同时对照采用稿/规则和同类已统一页面；发现漂移先定位层级与样式来源，修正后覆盖受影响调用者。具体判读按[严格截图流程](walkthrough-guide.md#严格执行截图判读与跨页一致性)。

### 组件复用与选型

界面开发先读取项目组件规范、目录、状态示例、允许变体和实际实现，再决定组件边界。按用户要求采用奥卡姆剃刀原则“如无必要，勿增实体”，将新增实体的必要性写清楚；不能只因需求、页面或作者不同就复制同类型控件。

| 当前情况 | 优先选择 | 需要说明与验证 |
| --- | --- | --- |
| 已有约定组件满足需要 | 直接复用其接口、语义样式与行为 | 在当前内容量、状态、输入方式下仍适用 |
| 现有组件可由组合或小幅扩展满足 | 组合已有部件，或新增有明确语义的变体 | 保持既有调用兼容；检查受影响使用者，避免拷贝实现只改名字 |
| 通用需求尚无约定组件 | 检查已有依赖；评估成熟三方组件，或提炼最小公共组件 | 明确共同用途、接口和例子，接到项目公共目录；不为每个功能建独立控件体系 |
| 需求确有不同语义或性能约束 | 新增专用组件或独立变体 | 说明现有能力的实质缺口；相似外观不必强行共享业务逻辑 |

公共库优先建立在项目已有目录/包中，包含实际使用的控件、行为及状态示例；没有跨仓发布需要就不新增独立仓库、包管理或发布体系。以已知共性提炼，业务差异放在合理的组合与业务组件中。不要创建大量布尔开关的万能组件，也不要为转发所有属性而套没有价值的包装层。

第三方库是允许的实现选项。优先沿用技术栈中已选且满足要求的库；需要新选型时核对官方文档及维护状态、当前框架版本、平台/SSR兼容性、关键行为和可访问性、许可与维护成本。性能检查包括实际构建后的增量体积、按需引入效果，以及代表数据量下的渲染/更新、内存和交互表现。“成熟”“知名”都不能替代本项目验证，也不保证比自建更轻。

做一个范围有限的代表场景验证再决定：列出复用/扩展/引库/自建候选、能力缺口与成本，记录采用理由和边界。必要的适配层用于统一项目行为和主题，不复制库内部实现。不在同一项目无理由引入多套重复的基础控件库，也不因 Skill 示例更换已有库。

React 的组件划分指导强调职责与数据关系；Vue 性能指南提示应以实际构建核对依赖增量成本。这里提炼为跨技术栈的复用判断，具体 API 仍按项目选用框架核对。[React 指导](https://react.dev/learn/thinking-in-react) · [Vue 性能指导](https://vuejs.org/guide/best-practices/performance.html)

### 按实际需要落地

有实现授权时，在现有技术栈中完成一条代表流程，按已确认需要提炼下列共用能力；仅设计时给出位置映射与待实现状态：

- 应用外壳：稳定导航、当前对象/位置、主要内容容器及适用的辅助区域。
- 布局模板：本轮真正复用的页面或工作区结构，明确区域职责、伸缩与滚动归属。
- 语义样式变量：从既有字体、色彩、间距与层级约定接入，不在各页新增同义值。
- 组件与行为：复用已有按钮、字段、展开控件等，并统一焦点、表单校验、反馈与恢复的相关逻辑。
- 代表页面与状态样例：典型内容、长内容、错误及角色差异，在页面中验证组件；有现成组件展示工具就复用，没有时用项目的轻量示例方式。

组件规格至少说明：用途与不适用情况、输入/事件、允许的变体、状态与转换、数据保留、可访问名称/键盘/焦点、响应式行为。选择关键状态检查，不要求每个控件都有所有状态。避免仅为包一层样式制造空抽象，业务判定也不要塞进通用视觉控件。

对大列表、表格、编辑器、画布、流媒体等规模敏感的组件，补充代表数据量、性能目标和测量方法。是否分页、虚拟化、分块或延迟加载取决于已确认瓶颈与任务约束；具体约定按[性能指导](performance-guidance.md)记录，检查这些策略对查找、选择、焦点和数据正确性的影响。

部件和完整页面应相互校验，尤其是正文长度、数量和角色变化。此处借鉴 Atomic Design 的整体与局部往返思路，不要求采用其命名层级或按层线性施工。[作者公开章节](https://atomicdesign.bradfrost.com/chapter-2/)

## 6. 验证、接入与维护

先验证代表流程，再检查有同根因或同组件影响的页面。测试应覆盖会出错的行为约定，例如保存失败保留输入、关闭后焦点去向、返回列表恢复筛选；可逆的纯文案/样式修改不机械补测试。

规则状态与缺陷状态分开：规则可为“候选 / 已采用 / 待替换”，并另记实现与验证覆盖。文档写入不代表用户已理解；组件测试通过不代表所有业务页面已接入。真实用户观察、Agent 走查、自动测试和静态检查分别标注。

修改共用约定时，同步规则、实现与示例，将暂未迁移页面列入 checklist，说明原因和恢复条件。记录例外的场景与证据；复用多个页面的合理例外可成为命名变体，不能通过不断新增特殊样式逃避统一。

完成后，应能从一个规则 ID 找到采用理由、共用实现、代表页面、有效证据和未覆盖范围。这样下一会话可沿用项目基线继续设计。
