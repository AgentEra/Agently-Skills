# 设计与方案文档的画板表达

遵循统一入口的“面向人的表达原则”：先用图组织足够完整的信息，以分区、关系、就近标注和说明降低阅读成本。优先一张综合图或同一连续阅读面；绘图方式优先白板图、原生图形、HTML+CSS、SVG或图文混合，尽量不使用 Mermaid。一般图示在用户明确要求或载体限制确需使用时说明原因；下述技术架构图默认指定 SVG，不因载体限制或生成方便改用 Mermaid。不能牺牲边界和关系的表达。不以拆图来掩盖总览缺项，也不靠缩字号把全文塞进一张图。本文的风格偏好来自用户约定，图型选择与验收流程是本 Skill 的应用方法。

## 1. 先确定图要回答的问题

写清目标读者、此刻要理解或决定的事、图所依据的版本及已知事实。先列对象、关系、条件与边界，再安排布局。缺失的日期、依赖、权限和失败行为标为待定，不为让图完整而虚构。

| 要解释的问题 | 可用图型 | 语义检查重点 |
| --- | --- | --- |
| 从哪里开始，如何分支和结束 | 流程图、UML 活动图 | 起止、条件、分支标签、汇合及必要异常路径 |
| 谁负责，交接给谁 | 泳道图 | 泳道代表角色/组织/系统的含义一致；交接对象与完成条件明确 |
| 谁先调用谁，何时返回 | 时序图 | 参与者、时间方向、同步/异步、返回、循环/条件及失败恢复 |
| 未另指定视图的技术架构梳理 | SVG 逻辑分层架构图 | 自下而上、自左向右表达逻辑支撑，层名、职责、依赖与边界明确，不画成流程或部署拓扑 |
| 明确要求结构、状态、职责或部署关系 | UML 的适用图型，如类图、状态图、组件图、部署图 | 明确图型及符号含义；关系类型不能只靠箭头猜测；简化记法须说明 |
| 何时做、持续多久、哪些是里程碑 | 甘特图 | 日期/时间尺度、工期、依赖、里程碑与实际/计划状态；估计不冒充承诺 |
| 活动之间如何制约、如何计算计划 | ADM/PDM 计划网络图 | ADM 用箭线表示活动，PDM 用节点表示活动；依赖类型、延迟及假设明确，不混用两套语义 |
| 内容如何分区，操作和状态怎样变化 | 界面线稿、布局稿、交互稿 | 核心内容/主动作、归组、空间、入口与返回，以及相关收纳/展开、错误/加载等状态 |

ADM/PDM 在本表按项目计划网络语境理解；其他领域可能使用同名缩写，先按项目语境核对。UML 也不是单一图型，不能把任意方框图自动称为符合 UML。声称关键路径或总工期时，须有真实依赖、工期、日历等计算依据；画出连线并不等于完成计划计算。

流程或协作图按问题补齐数量关系（拆分、汇合、一对多/多对多）、并行范围与容量、排队入口与潜在积压、关键决策的准入方式与责任、失败返回及积压处理。画出关系和位置，不只列步骤名；用不同符号区分质量/授权门槛与容量调度，避免把所有判断误画成人工审批。未知上限或阈值标为待测/待定，不为图完整而编造数值。

一个人同时管理多项诉求时，先画人到多项诉求的关系，再展开单项内部；不要让单项生命周期掩盖管理者的并行负荷。信息模型须同时检查纵向推进和横向对齐：公共规范、共享Spec、接口/数据契约、其他文档及诉求间依赖由谁维护，各项引用哪个版本/条款，变更后如何判断影响、通知责任人、更新证据及处理矛盾。避免只有孤立任务档案、没有共享依据与跨项关系的模型；链接存在或消息送达不等于已经对齐或批准。

标明各对象的稳定身份、版本、事实来源和维护权，区分业务决定、Agent执行计划、工程运行事实及其映射；跨边界消息箭头不自动代表数据库基数。时序和容量推演区分实测、用户前提与演算参数，显示阶段时长、在途数量、队列变化、触发条件及返工路径。用可复算事件支撑峰值与等待时间，说明额外到达和例外是否计入。每处卡控说明防止的具体失败、依据、执行者及代价，不能把容量调度或状态记录误当新增人工审批。

确需多张图时，以可独立理解的综合总览加局部展开组织，核心数量、准入、异常和责任仍在总览就近可见。保持对象名称和稳定标识一致，不要求读者自行跨图拼装主流程。界面交互稿要说明触发与反馈，不只提供几张彼此无关的静态页面。

### 架构与流程图的默认表达

**技术架构：默认看逻辑分层，用 SVG 绘制。** 用户只说“梳理技术架构图”时，不先要求用户挑图型；从可查资料识别能力、职责与支撑关系，输出 `.svg` 文件。基础能力在下、依赖它的能力在上，横向展开从左向右表达逻辑支撑；层数和分区依据实际系统，不硬套固定四层/五层，也不把无依赖的同层模块强行连成顺序。

- 层与块用职责或能力命名，必要时在块内列关键模块和所用技术。不能只摆技术 Logo 或产品清单，让读者猜这些能力怎样共同工作。
- 区分“支撑/依赖”与“请求先后/数据流”。箭头说明关系，方向与所声明语义一致；不把分层图画成所有请求必须逐层串行经过的流程图。必要的跨层依赖与外部系统有明确边界，不靠强行塞入某层掩盖。
- 用户明确需要部署、时序或其他视图时按其目标选择，不将每种架构视图强改为分层；没有特别指定时不拿部署拓扑、调用流水线或代码目录树代替逻辑架构。
- 默认架构图直接用 SVG 的形状、文字、分组和连接绘制，不使用 Mermaid 绘图或把 Mermaid 自动导出当作满足要求。SVG 不能只是包装一张位图。保留可修改的 SVG 源，实际打开渲染结果，检查文字、箭头、裁切及缩放可读性；SVG 可解析不等于画面通过。载体无法内嵌时仍交付 SVG，可附受支持的预览，不自行换成 Mermaid。

**流程图：先辨认主链路，再组织次要链路。** 主链路是完成当前业务目标的关键职能及交接，不是把所有动作依次排开。按业务职责/输入输出划块，例如“受理申请”“评估与决定”“执行交付”；块内用短句说明核对资料、形成意见、记录结果等细节，不把上传、点击、写日志等全部升为同级节点。某个条件、交接或异常会改变责任与结果时，仍须作为必要关系清楚表达。

- 主链路沿一条容易连续阅读的方向排列，节点和连接有稳定的视觉重点。反馈、回访、补充信息等次要链路靠相关职能外侧或次要通道布局，写清触发、返回点和影响，避免来回穿过主链路。
- 用位置、线型/粗细和简短标签区分主次，不只靠颜色；图例说明当前符号含义，不把“虚线”自动等同于异步、可选或不重要。主次取决于当前任务，不能将批准前提、失败恢复或决定依据因视觉降级而隐藏。
- 块标题说清谁做什么或承担什么业务职能，连接写实际条件/结果。默认不用 H1/H2、N1/N2 等无含义英文编号作为可见主标签；真实 API、协议、系统名和必要技术缩写保留准确名称，并在读者需要时解释。追踪 ID 可留在元数据或工作记录；确需在图中引用时伴随易懂名称，不能要求读者反查编号表才能读图。
- 细节较多时先按职能在块内分组与就近注释，再选择必要局部展开。总览保留理解主流程所需的关键条件、异常去向与责任；不能用“一张综合图”作理由平铺全部细节点，也不能收纳后只剩空泛步骤名。

验收时，先让目标读者指出各层“谁支撑谁”，或沿主链路复述“从哪里进入、经过哪些职能、何时交接、结果是什么”，再读反馈/异常如何回到主链路。若先看到的是密集交叉线、编号或等权细节点，先重排粒度、主次和命名，再检查样式。

### 关系与边界的必查项

涉及流程、架构或协作关系时，下列四个维度是设计与审读的必查项，先核对语义再布局；确实不涉及某个维度时说明适用范围，不为凑图虚构系统或模块。

| 维度 | 必须想清的关系 | 图中如何让读者直接看见 |
| --- | --- | --- |
| 逻辑关系 | 触发、前提、输入输出、顺序/并行、条件与汇合；按影响补齐失败、取消及恢复；区分运行时调用、配置导入、数据流和控制流 | 标注箭头的具体含义、方向、条件与结果；必要返回路径就近可见，不把依赖线全部画成先后步骤 |
| 系统边界 | 哪些属于当前系统，哪些属于外部系统；哪些交互跨越信任、进程或部署边界 | 使用有名称的边界框或泳道包住所属对象；明确边界种类，跨界连线标注接口、传递内容及适用的校验/失败责任；边界不能只靠底色辨认 |
| 归属关系 | 数据与规则由谁权威维护，谁决策、执行、审计和处理失败；代理、导入、共享执行与最终责任是否不同 | 将模块放进真实所属系统/角色区域，必要时就近标注维护者与责任；不把“可读取/同步”画成“拥有/决定”，不凭部署位置推断业务权威 |
| 模块关系 | 包含、组合、依赖、调用、共享和替换关系；模块的职责、接口与上下游约束 | 用嵌套、分组和不同关系标注区分结构与流程；逻辑模块不自动等于独立进程或微服务，适配器位置及替换范围明确 |

同图混合多种关系时提供简短图例：框表示什么边界、箭头表示什么交互、虚线表示可选还是异步；同一符号保持同一含义。总览必须看见影响结论的边界与归属，不能只在图外说明“实际属于某系统”。

## 2. 按阅读任务选择表达语汇

品牌、演示和传播材料还可按[视觉叙事与载体选择](visual-storytelling.md)使用主张卡、聚焦字标、图标条目与机制对照图。是否使用画板由图文表达和后续编辑需要决定，不限于工程流程图。

| 表达需要 | 可选语汇 | 实际表达方式 |
| --- | --- | --- |
| 降低阅读压力、帮助讨论 | 手绘文字与白板 | 适度手绘线条、轻量分区和少量强调色；允许候选与批注，但布局、术语和连线仍须清楚 |
| 强化对齐与稳定的信息层级 | 简约网格 | 规整几何、稳定网格与对齐、清晰文字、克制配色；可与白板风格结合，保留影响理解的假设与边界 |
| 准确辨认代码与技术标识 | 局部等宽文字 | 代码和标识使用等宽字体；模块边界、网格和少量语义强调帮助阅读，不要求整份材料采用技术主题 |

上表是可选表达语汇，不是按受众强制分配风格。依2026-10-29用户约定，面向人的表达优先考虑手绘文字、白板风格来降低阅读压力；外部材料或技术读者也适用。明确的品牌、正式建模记法或当前任务要求另作约束。不要为了“极客风”强制黑底、荧光色、密集字符或低对比文字。中文使用可读的字体回退，代码标识保持准确；手绘不能模糊箭头、日期、关系基数或交互状态。

在工具允许的范围内调整线条规整度、字体、描边、填充、对齐和间距。检查实际字体及导出效果，不按风格名称假定工具已实现所需外观。同一套材料保持共同视觉规则，业务差异以图例和语义表达。

## 3. 使用画板与保留可编辑源

- 沿用项目已有画板和正文来源，先读取实际内容及修订，不因新一轮讨论另造平行“最新版”。已明确的新候选可以独立保存并标注状态。
- 使用 RioWork 时，先发现当前 MCP 能力并读取其实际协作/权限约定；核对目标项目、资料目录、对象与授权，按当前工具合同创建或更新原生画布。保存前读取版本，保留原有元素身份与图片资源，处理并发冲突后再改；创建/保存后读回。具体工具名和字段以当前接口为准，不在 Skill 中固化连接 ID。
- 没有 RioWork 或用户选择本地方案时，可以交付兼容的 `.excalidraw` 源文件及必要的预览。兼容性应在目标编辑器实际导入、打开、编辑和重新保存后确认；JSON 可解析并不能证明兼容。
- 优先用原生形状、文字和连接表达节点、关系、泳道和界面框架。保存元素绑定、分组、层级与引用资源；导出的 SVG/PNG 用于阅读，不能用一张截图冒充可编辑图。若图片含嵌入场景数据，也需实际重新打开验证。
- 需要精确语义的 UML、计划计算或较大图，可使用合适的专业工具/文本源生成，再核验导入结果。不要假定 Mermaid 等转换覆盖所有图型，也不要假定白板会自动验证 UML、计算依赖或关键路径。
- 与 imagegen 配合时，图像可用于外观探索或素材；精确标签、关系和可修改布局仍以可编辑结构承接。线稿表达结构，交互稿表达行为，采用稿与真实实现分别标记。
- 制图授权不自动包含公开分享；依用户明确的交付对象和位置保存。使用既有写入授权无需重复确认。只有图形方案或本地文件时，如实说明尚未写入远端画板。

Excalidraw 的场景格式及导出 API 会随版本变化。实施时查当前项目依赖与宿主支持范围，不为套文档示例升级全项目或硬编码未经核验的字体/元素枚举。

## 4. 把图和正文一起走查

1. **语义**：按目标角色沿图逐步复述，并逐项检查[关系与边界](#关系与边界的必查项)。读者应能指出每个关键模块在哪个系统内、谁维护规则与数据、谁作最终决策及执行、跨界交换什么、主要逻辑与失败如何衔接；与图意有关的答案不能依赖作者口头补充。检查节点/参与者、箭头方向、条件、责任、顺序、日期及状态与正文一致；没有连线不应靠读者猜测。区分当前实现、候选设计、示例和未定内容。
2. **阅读**：在目标载体的实际显示尺寸查看总览与必要局部。判断分区、主次、字号、对比、连接交叉、遮挡、裁切和空白是否合理，同时检查完成一次理解需要跳转几次、是否要记住前图再拼装后图。先调整分区、层次与就近说明；不要靠缩字号或删除关键关系挤进一页。必要的局部展开保留在同一连续阅读面，拆分不能把总览降成空泛步骤表。
3. **可编辑性**：重新打开源画板，抽查相关节点、文字和连接可编辑；移动节点检查关系绑定，确认图片资源仍完整。只对实际受影响的能力验证，不破坏原业务内容。
4. **正文衔接**：图放在相关论述处，配最少必要的图名、图例或读图说明。删掉图或无法访问画板时，正文仍保留核心结论、必要条件与下一步；复杂关系可由图辅助，不靠裸链接代替说明。
5. **交付**：核对画板修订、正文版本与导出快照一致。公开版检查批注和嵌入资源的受众范围，避免把内部讨论材料一起带出。记录具体观察、缺陷、修订和原路径复验，不以“图已生成/已保存”作为验收。

正文、自主编辑、导出视觉和目标宿主兼容分别下结论。工具或环境不可用时保留待验范围；不宣称已经在 RioWork 保存或已完成导入验证。可在[文档记录模板](../assets/document-review.md)的图稿表中跟踪，不另建重复问题库。
