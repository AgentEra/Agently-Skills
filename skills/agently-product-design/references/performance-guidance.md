# 场景性能约束与测试

开发中用真实任务和规模决定性能要求，在功能相对成熟时主动建议针对性的性能与压力测试。本文给出可执行方法和有来源的参考值；参考值不自动成为项目承诺，文档、计划或测试脚本不等于实测通过。

## 1. 场景核对与性能建议

先查项目已有性能约定、监测、发布构建及测试工具，复用仍有效的基线。针对当前影响范围核对：

- 核心任务与等待容忍度：哪些是点击/输入后的即时反馈，哪些是保存完成、后台计算或长任务；哪些失败会造成业务中断。
- 用户环境：主要设备、浏览器/原生客户端、硬件能力、网络/地域与冷/暖启动；低端或弱网是否在支持范围。
- 数据规模：典型与高位数量、正文/图片/文件体积、列表/画布复杂度、增长速度、缓存与存储规模。
- 使用负载：活跃与同时在线用户、操作频率、读写比例、峰值请求到达率、突发/长时间使用、协作连接及重连；在线用户数不等于同时操作数或每秒请求数。
- 部署条件与预算：服务规格、实例/连接/队列约束、扩缩容、外部 API/模型配额、观测能力及测试成本。

从项目可查明的事实直接读取；关键未知向用户核对，优先询问会改变目标的少量信息。用户已有答复可沿用，不每次重复问。信息不足时给出可调整的规模档或假设，清楚写“待确认”，不编造并发、响应时限或成本承诺。

向用户提出具体建议：“这个任务在这些设备、数据量与负载条件下，建议达到什么体验/服务目标，如何测、实现代价是什么、需要确认什么”。目标描述宜同时包含绝对体验底线与合理的回归预算；只说“提升 20%”无法判断是否已经足够快。确认后的目标写入项目规范与同一 checklist。

服务的测量指标（SLI）描述实际测什么；目标（SLO）描述在什么时间窗口内达到什么程度。可用性、延迟与代价的取舍需要业务和开发/运维共同理解，不能自动承诺所有服务达到某个“几个九”。[Google SRE：Implementing SLOs](https://sre.google/workbook/implementing-slos/)

## 2. 五个层面的约束

| 层面 | 选择与任务相符的指标 | 测量与保障 |
| --- | --- | --- |
| 界面加载 | 初始关键内容出现、页面/路由可用时间、资源体积与请求链；Web 可用 LCP | 发布构建、典型/低端设备、冷暖缓存与目标网络；控制关键资源，按证据优化图片、依赖、加载顺序 |
| 操作响应 | 输入/点击到可见反馈、到业务结果的端到端时延；Web 可用 INP辅助 | 实际操作与时间标记，拆分前端主线程/网络/服务耗时；及时且真实的反馈不替代完成时间 |
| 交互流畅性 | 滚动/拖拽/缩放帧时间、卡顿/长任务、视觉位移、持续使用内存趋势 | 在代表内容与设备下录制运行轨迹；按瓶颈减少不必要渲染、布局或计算，检查焦点与可读性 |
| 服务稳定性 | 有效请求/用户任务成功率、超时、尾部延迟、恢复时间、数据正确性、连接可靠性 | 按窗口和任务分类监测；定义错误口径；验证超时、重试上限、幂等、取消与恢复等适用策略 |
| 服务抗压 | 约定峰值吞吐/到达率、并发任务/连接、排队与资源饱和、峰值下延迟/错误、卸载后恢复 | 代表负载测试与资源观测；验证有界队列、限流/背压及降级等实际需要，避免无上限重试与堆积 |

延迟通常报告 p50/p95/p99 等分位数及样本量，不只平均值；失败与超时不能从总体悄悄移除。吞吐量应说明请求还是完成的业务任务。容量是在满足既定正确性、延迟和错误目标的条件下可持续承担的负载，不等于崩溃前最大请求数。

## 3. 业内参考与使用边界

2026-10-14 核对的一手参考：

| 参考 | 常见参数/方法 | 项目应用时须说明 |
| --- | --- | --- |
| [Core Web Vitals](https://web.dev/articles/vitals) | 良好参考：LCP ≤ 2.5秒、INP ≤ 200毫秒、CLS ≤ 0.1；以真实访问第75百分位，并按移动/桌面区分 | 用于 Web 加载、响应与视觉稳定性的参考。LCP不等于业务就绪，INP不等于服务完成耗时，CLS不等于帧率；应用路由、画布等另补关键任务指标 |
| [Rendering performance](https://web.dev/articles/rendering-performance) | 60Hz 下每帧约16.7毫秒，是整帧预算；显示刷新率改变时预算随之改变 | 按目标设备/任务测帧时间和卡顿，给浏览器及系统留余量；不能把60fps作为所有页面/设备的通用合同 |
| [Google SRE：SLO](https://sre.google/workbook/implementing-slos/) | 从用户需要、现有测量和资源代价形成可用性/延迟等目标与窗口 | 没有通用服务p95、QPS或可用性承诺。写清来源、统计口径、假设与确认状态 |
| [k6：负载测试类型](https://grafana.com/docs/k6/latest/testing-guides/test-types/) | 从小规模烟测确认脚本，再按正常负载、压力、突发、长稳或容量探测的风险选择 | 不照抄示例虚拟用户数/时长；用户、请求与业务任务的负载模型不同 |

实际使用前按相关指标的当前官方定义核对更新。以上参考值不证明当前应用已经达标。实验室测量可定位问题与回归，真实用户测量反映实际分布；二者条件不同。单次 Lighthouse 分数不代表所有页面或真实用户体验；没有输入交互的加载审计无法直接测 INP，TBT等代理指标也不能冒称INP。

## 4. 随开发建立适度的测试机制

将范围相称的目标与测量接到已有工具链，不为一次小修改建立整套性能平台。用[性能计划与记录模板](../assets/performance-plan.md)或项目已有章节记录：

1. 目标任务、代表条件、已确认/待确认目标与比较基线；数值来源和测量起止点清楚。
2. 可重复的测量入口、脚本/命令、测试数据及环境；记录代码/制品/依赖版本，使用有代表性的发布构建，注明开发模式或仿真限制。
3. 适用的前端/服务端观测：交互轨迹、端到端时间标记、延迟/错误/吞吐、CPU/内存/连接/队列/数据库等待；能定位哪层受限。
4. 按影响安排回归：轻量构建/资源预算、关键交互测量、服务低负载基线等可接 CI；更昂贵的负载测试在约定阶段执行。环境噪声较大时保留多次分布与容差，不用单次小波动判失败。
5. 门槛失败关联具体任务与证据，先定位瓶颈再改，修复后复用相同条件比较；发布后有条件时接入真实监测及适用告警。

依赖与组件选型也要测真实增量体积、首次使用延迟及代表数据量下的更新/内存表现。分页、虚拟化、缓存、延迟加载等都是候选，按已确认瓶颈选用，验证选择、搜索、焦点、数据新鲜度与权限等相关正确性。不要提前重构所有页面或随手加缓存来宣称完成性能优化。

## 5. 功能相对成熟时主动建议测试

核心流程及其错误/恢复语义稳定，代表数据、依赖和部署拓扑可复现时，向用户建议一轮性能和负载/压力测试，说明为什么此时值得做、测哪些任务、目标负载/持续时间、所需资源成本及交付标准。尚不成熟时记录哪些条件满足后再建议；不等发布后才发现容量问题，也不在无关的单点修改后例行推销全量压力测试。

按业务风险选择测试，而非强制全部运行：

- 小负载烟测：核对身份、场景和结果断言、脚本及观测有效，再扩大负载。
- 正常/峰值负载：验证预计业务量下的延迟、错误和正确性。
- 压力/容量：逐级增加至约定边界，观察瓶颈、拒绝/降级及卸载后恢复。
- 突发：对集中上线、批量任务、协作重连等实际突发进行验证。
- 长稳：对长期连接、持续编辑、泄漏或队列增长风险进行验证。

负载模型写清开放到达率还是固定虚拟用户循环、思考时间、读写比例及持续连接。循环用户在服务变慢时会自然减小请求速率，可能掩盖过载；到达率模型则须报告未能启动的请求/迭代和压测机瓶颈，避免把未生成的流量算作被服务成功承担。模型指导见[k6 开放与封闭模型](https://grafana.com/docs/k6/latest/using-k6/scenarios/concepts/open-vs-closed/)及[内建指标](https://grafana.com/docs/k6/latest/using-k6/metrics/reference/)。

负载测试不能仅访问健康检查，也要包含业务比例与关键写入结果断言；连接/协作/流式任务按实际协议与生命周期建模。确认压测机、网络和外部配额没有先限制结果。替身可测本地承接，但不能证明真实依赖的吞吐、延迟或配额。

## 6. 执行边界、结果与交接

普通开发中可在授权范围内建立脚本和隔离环境轻量测试；高负载测试须核对目标环境、授权、资源成本、数据隔离及停止条件。已授权就继续执行，不每阶段重复询问；新涉及共享/生产服务、外部付费调用或故障注入时先确认相应范围。建议压测不等于获准对线上发流量。

测试前写清最大速率/并发/时长与错误、资源、队列等停止条件；保存真实数据，控制合成数据和后台任务，结束后清理测试产生的记录/任务并核对服务恢复。先准备具体可审阅计划，再请求尚缺的执行授权。

报告计划负载与实际到达/完成量、失败/超时、分位延迟、资源和队列趋势、业务正确性、恢复、成本及环境差异。结论只覆盖测试条件；短期通过不能证明月度可用性，单机容量不能直接外推集群，同一设备/内容下的性能也不能代表所有用户。

将未达标项与未测条件写入同一 checklist，注明根因是否确认、下一步和可复用证据。交付分清“机制已建立”“实测通过”和“规模待确认”。新增相关依赖、组件或数据规模后重验受影响项；无变化且无新证据时复用历史结果。
