# 共用审读与修订规则

应用、方案与文档的共同规则唯一维护在此。按任务取必要字段，沿用项目记录；不让填表取代工作。

## 文档制品与产品界面的验收范围

先按实际用途与交付约定区分产物，再选择验收；HTML、CSS、SVG、画板或少量交互只是表达载体，不能据此把文档升级为产品界面。

- 一次性报告、评审方案、图解、演示等文档制品，默认检查事实、论证、信息自闭环，以及实际交付阅读容器中的图文可读性、资源和必要交互。保持用户要求的图文表达与正常阅读质量，不把缩小范围理解为免做呈现检查。
- 文档的深浅主题、手机／宽窄视口、多背景、导出等专项检查，须有用户明确要求、已确认的真实使用载体条件，或已发现的相关缺陷作为依据，且只覆盖受影响条件。不能从“可能有人在手机或深色主题阅读”推导例行矩阵；真实要求不明确时沿用当前交付条件，不为可选检查阻塞分析和写作。
- 不为凑齐验收主动新增主题切换、字号档位、多设备版本或导出模式。已有或用户要求的必要交互仍须按用途验证。交付包含导出文件时检查该文件；没有导出要求时不另造导出版本。
- 实际产品页面、公共组件，以及复用到产品工作面的制品，继续按受影响工作面、既有规范和代表状态完成适用的功能、交互与视觉验收。真实窄容器、多主题或多背景使用条件必须检查；文档例外不豁免产品验收。
- 清单记录实际交付容器与专项检查的触发依据即可，不给每份文档铺满不适用项。混合任务分别确定文档和产品部分的验收范围；本规则是范围的唯一维护入口，下级清单中的“实际／适用”均依此解释。

## 信息自闭环与角色知识边界

任务、评审、需求、方案及页面/文档主体必须让目标角色不离开当前阅读面、不打开外链也能理解。选择有实际知识、权限或责任差异的角色，说明其合理已知信息、可见内容、当前目标及完成标志；作者聊天、旧方案与内部编号不自动成为读者背景。同一人切换责任时也要检查知识前提。角色模拟不要求多 Agent，不冒称真人测试。

1. 仅凭主体复述：为何提出，处理什么对象/范围，必要背景和条件是什么，依据与结论是什么，谁需决定/行动，还有哪些未定条件。
2. 指出具体缺失与后果：未说明的指代、定义晚于使用、事实到结论的跳跃、隐藏的条件/后果、只在外链出现的关键依据。链接有效不能让本项通过。
3. 补回最小充分背景和逻辑衔接；外链保留作深读。必要背景属于主体，不按装饰性副标题或重复说明删掉；也不粘贴全部日志和历史。长文按整份材料及可独立进入的摘要/任务页检查，不要求每段重复背景。
4. 保存后重新打开实际文件/页面，沿原角色及相同知识边界复读，记录“角色与已知→实际理解/卡点→具体缺失→修订→复验”。只读本地草稿不能证明远端正文已更新；缺少读取条件保留待验。

涉及流程或关系图时，按[画板的关系与边界必查项](diagram-and-board.md#关系与边界的必查项)让同一角色仅凭图与当前正文复述逻辑、系统内外、权威与执行归属、模块包含及依赖；发现边界或责任只能靠作者解释时，先修订原图再沿原角色复验。

正文理解、事实正确、呈现可读各自成立。未通过不能声称信息完整；不能把“等用户检查”当作已授权修订的完成条件。

## 评审修订的完整性与表达承接

修订稿是可独立阅读的新版本，不是给看过原稿的人补几条变更。修订前固定原稿、有效图文和本轮意见，按仍然有效的内容比较覆盖与表达质量。

- **保持相称的信息密度和结构。** 保留有效的背景、目标、判断依据、方案机制、角色与操作后果、异常边界、图表及验收条件；不得默认把修订降成提纲、短摘要或纯文字。信息密度指读者在实际阅读空间能获得的有效信息，不是字数、块数或缩小字号。新逻辑需要重组时可以调整结构，但须说清保留、移动、替代与删除的内容及理由，不机械保留已失效内容。
- **不借用旧稿上下文。** 即使评审人参与过上一轮，也按未读过原稿的合理知识边界补齐本版必要前提。“其他不变”“按上版”及历史链接不能代替主体。简短变更说明可帮助比较，但必须与完整新版并存，不能成为唯一交付。
- **图文一起修订。** 影响流程、布局、关系或关键状态的变化，要同步相应图稿及采用说明；旧图仅作历史比较时明确标注，不冒充当前方案。用户要求 Imagegen，或新视觉探索有助于判断实质变化时，执行生成与判读；纯文字小修和仍然适用的图稿不必重复生图。不能把生成图当作实现或运行验收。
- **整稿与差异分别检查。** 逐项对照原稿的有效信息和本轮诉求，确认没有在重写中丢失依据、否定、分支或责任，再检查本版主线是否连续。保留历史与新旧关系，不以不断新建摘要掩盖内容流失，也不让读者跨版本拼装当前规则。
- **保存后按新读者复读。** 重新打开实际保存的完整正文及图稿，仅凭本版说明复述问题、取舍、流程、后果、待定条件和下一步，并记录“原稿有效内容→本版去向/改变理由→无旧稿复读结果”。漏项或图文冲突先修订复验；文本审读、图稿判读和真实运行验证各自保留结论。

## 一套事实与稳定问题编号

跨 Skill 的会话进度与变更历史沿用已安装 `agently-collaboration` 的协作记录；这里定义产品/文档问题的字段和验收状态映射，不另造第二份总账。单独安装时继续使用下述最小清单即可。


沿用已有清单；没有时使用[共用记录模板](../assets/delivery-review.md)。模块模板是同一记录的视图，已有总表则引用原 ID，不重复建事实、状态或问题表。

每项保留：稳定 ID、对象/位置和版本、角色/故事与条件、预期与实际、用户后果、原因及其证据/假设、修订/方案、可观察验收、证据、状态和未完成动作。方案推理可补观察→原因→机制→效果→验证联系。不要只写“已优化”“逻辑通顺”。

状态沿项目约定；无约定时使用：

`待查 → 已复现/待设计 → 修订中 → 待复验 → 已验证`

证据不足为待查；确认缺陷才为已复现；设计取舍为待设计。受阻、暂缓、不适用需写原因及恢复条件。仅满足该项验收标准才可勾选 `[x]`；写完代码、生图或无关测试通过均不能勾选。失败保留原证据并退回相应状态，反馈或基线变化推翻结论时重开原项，不另建一个 ID 掩盖失败。

优先级依据用户影响，沿项目定义；没有时可用 P0 数据损失/越权/核心任务不可完成，P1 主动线受阻/误导，P2 局部理解或操作摩擦，P3 低影响润色。可调整，不机械把设计偏好列为缺陷。

同根因可以统一修复，但仍复查受影响角色、路径与产物。混合验收可在原项下分维度/子项，避免一种证据掩盖另一种未验。

## 证据与交付边界

记录实际版本/环境、方法、输入/动作、结果、证据位置及能证明和不能证明的范围。区分真实运行、自动测试、fixture/协议仿真、静态检查、设计推演、用户反馈、真实用户研究。模型模拟不是真人理解率，候选图不是已实现界面，结构或安装校验不是方法效果证据。

未变化且条件仍适用的证据按影响复用；相关代码、正文、依赖、配置、环境或输入变化后只重验受影响部分。缺证据为待验，不把未知判通过。

交付前对账：本轮必须完成的项是否有当前证据，新问题是否入账，未完成项是否说明影响、缺口、下一动作和责任。正文/论证、应用功能/交互/视觉、操作复现、图稿可编辑性、成品渲染与多格式同步按适用范围分别结论。文档制品按本页验收范围检查，不自动运行应用验收；涉及真实产品运行却缺少条件时只能交候选或审查结论，不把整项验证交回用户。
