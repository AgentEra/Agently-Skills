# 三类走查：从一个故事检查到结果

按故事需要选取检查点。三个视角共享故事 ID 与证据；无需创建三份重复缺陷表。

纯文档撰写/审查按[文档表达模块](../modules/document-expression.md)检查内容、逻辑和阅读体验。下方功能、交互及运行截图流程适用于应用界面；文档成品另按其实际格式验收，不混用完成状态。

## 信息自闭环：不跳页的读者走查

任务、评审、需求和页面主体按[共用审读规则](common-review.md#信息自闭环与角色知识边界)执行；此处保留原锚点供既有引用定位，不另维护一套标准。

## 功能：行为与业务结果

沿入口、输入、状态变化、交接、持久结果逐步核对：

- 角色权限是否在实际命令端成立？隐藏按钮只是表现层。
- 作用对象、版本、范围是否清楚？批量操作是否误伤只读项？
- 作者、编辑人、批准人、执行人等责任是否按产品规则保留？
- 提交成功后，接手者是否能找到结果、来源和下一动作？
- 部分成功、重复提交、取消、撤销、版本冲突是否有真实定义？
- 刷新、重开、断线等在本轮范围内时，内容和进度是否正确恢复？
- 检索、导出、通知等承诺的后续出口是否与业务结果一致？

通过定义应落到具体结果，例如“审核者只批准第 3 版，申请者能读回条件”；“接口返回 200”不足以支撑该结论。

## 交互：在每一步问四个问题

1. 此时用户会想到做这个动作吗？有没有被迫猜产品内部流程？
2. 能在当前界面发现正确入口吗？角色、状态、空数据是否使入口消失？
3. 看见入口后，能理解它将产生什么结果吗？名称与作用是否一致？
4. 执行后能知道是否成功、现在在哪里、下一步做什么吗？

这是对认知走查方法的应用。设计者的角色推演可以发现学习障碍，但不能证明真实新用户都能理解。

再按产品补充：

- 反馈：加载/保存中/失败/等待别人是否区分？是否存在点击后无回应或虚假进度？
- 连续性：完成后是否回到合理上下文？折叠面板后能否找回当前任务？
- 动线合理性：为一次判断是否反复跨区找信息、开关面板或来回跳页？读取依据、操作、确认反馈是否相邻并顺序自然？不能只用点击数判好坏，也要看每次切换与记忆负担。
- 恢复：返回、取消、重试后草稿是否保留？重试会不会重复产生业务结果？
- 键盘：Tab 顺序、焦点可见、弹窗焦点、关闭后返回入口是否合理？
- 直接操作：选择、拖拽、菜单、滚动是否冲突？弹窗是否点穿到背景？
- 协作：别人改变内容后，本人是否误以为仍在操作旧版本？只读者看到的解释是否充分？
- 模式切换：专注/全屏、展开/收起是否在同一控件、槽位和锚定方位反向操作？进入后是否另造了异位退出、重复悬浮出口或只剩快捷键？按真实进入→退出→再次进入比较位置、焦点、草稿和宿主状态，不能只检查出口存在。
- 工具条一致性：同级图标的尺寸、间距、状态、命中和提示是否一致？直接入口与菜单收纳是否有任务依据？图标选择菜单与二元开关语义是否准确，切换是否引起邻项跳位？
- 一致性：同类动作在其他页面是否用相同名称、条件与反馈？同名“取消/关闭/返回”是否产生不同的数据结果？按项目规则检查，合理变体需有场景依据。
- 性能体验：加载、输入、搜索、保存、滚动/拖拽与持续使用在代表设备和数据量下是否响应及时、反馈真实？即时忙碌提示与业务完成分别计时；共用组件或数据规模变化后按[性能指导](performance-guidance.md)检查受影响基线。

涉及新的共用行为时，用[项目交互规范](interaction-system.md)将规则关联组件与代表页面。遇到复杂选项或多步流程，按[渐进式展示与布局决策](progressive-disclosure-layout.md)检查是否拆散了必要判断、收起内容是否仍可发现，以及每次选择是否足够明确。

## 视觉：检查信息组织、空间与多状态体验

先确定目标角色当前的核心任务、设备/窗口大小和典型内容密度，避免只看空壳首页。视觉检查既包括基本可读可操作，也包括易用性、动线合理性与信息组织质量。即使所有按钮能点、流程能结束，仍须评估以下维度。

| 维度 | 要判断的问题 | 可记录的观察与改进依据 |
| --- | --- | --- |
| 信息归组 | 同一任务、对象或判断所需的信息是否放在一起？无关内容是否因卡片/边框被误归成一组？ | 描述用户为一个判断需要跨哪些区域；以任务关系调整标题、邻近、层级和操作位置 |
| 堆砌与冗余 | 是否把所有功能、说明、状态、元数据同时摆出？同一信息是否重复且没有新的用途？ | 逐块写用途与使用时机；区分必要摘要/上下文重复与可合并的无效重复 |
| 文案干扰 | 标题下是否自动附带副标题、功能介绍或长段说明？是否重复按钮、字段或当前内容已表达的信息？ | 逐句说明删掉会缺少哪个必要判断；无增量信息则删除，普通操作靠命名与结构表达，必要条件与恢复提示就近保留 |
| 核心视图占比 | 当前真正要读、写、比较或操作的内容是否获得足够大的有效区域？是否被导航、说明、留白、工具和辅助面板挤成小窗？ | 在同视口、同数据、同状态下对照主内容有效宽高/面积或可见条目；排除被遮挡区域，注明估算口径 |
| 空间利用 | 分栏、边距、卡片嵌套、固定高度、工具区是否分配合理？是否存在局部拥挤与大片无用途留白并存？ | 标明拥挤/闲置区及原因，比较调整前后核心任务获得的空间和可读性；保留帮助分组与阅读的留白 |
| 收纳机会 | 哪些辅助信息/低频操作可折叠、进入抽屉、更多菜单或上下文工具？收纳后是否释放空间？ | 写清常驻内容、收纳内容、入口位置、展开触发和关闭方式；优先保留当前高频动作和必要判断依据 |
| 收纳后可发现性 | 用户能否知道里面有什么、是否有新消息/待办、怎样找回？是否多层收纳导致反复寻找？ | 检查标签/摘要/数量/状态提示，实走打开→使用→收起→找回；关键错误、条件和待处理事项不能无提示消失 |
| 状态变化与动线 | 展开、收起、选中、编辑、加载、错误、结果变化是否自然？是否移动目标、丢焦点或遮住正在用的主内容？ | 记录触发动作、变化区域、空间去向、焦点/滚动保留与返回路径；桌面和窄屏分别判断 |

主视图占比应足够大并符合当前任务，不设跨产品固定百分比，不以压小字体、缩小点击区或删除必要依据换面积。收纳有收益也有寻找成本；需要同时对照的信息应能一起看。若没有使用频率或用户观察证据，将“低频”“更省力”标为设计假设，安排针对性走查。

完整页面、控件及组件局部都可以成为检查对象。按实际设计采集默认/收纳、展开、操作中和结果状态；用连续操作判断这些画面之间的变化，不能靠一张静态全屏图下结论。将上述发现转成关联角色/故事的具体修订项，而非统一写“美化页面”。

比较优化前后时，除空间还记录入口寻找、错误选择、反复展开、跨区阅读及任务结果。数字指标按项目基线选；点击减少但理解困难，或主视图变大但判断依据被隐藏，都需要重新检查方案。真实用户观察、审查者判断与个人审美分开记录。

### 严格执行：截图判读与跨页一致性

以下是运行验收的必经过程。逐项用事实判断，记录在原 checklist；不用另写一套庞大报告。简单改动只覆盖受影响关系。

**A. 先定标准，再打开画面。** 写清当前角色想完成什么、默认必须看见哪些内容/条件及主要动作；列采用稿/规则和一个同类已统一页面。确认实际内容容器（不是整窗）、正常内容量及长内容、主题/字号、状态。无同类页面则沿项目页面族/主题规范，不虚构参照。

**B. 先看整页，再沿阅读顺序逐区检查。** 先不依赖源码解释，判断从画面能否识别对象、当前工作和下一动作；再按下表检查。每个受影响区域必须留下“观察→预期/标准→判断→动作”的简短结论，禁止只填“清晰、合理、统一、已检查”。

| 检查什么 | 必须从画面回答 | 不通过信号与下一步 |
| --- | --- | --- |
| 当前任务与优先级 | 第一眼读到什么、主要动作在哪里；当前需要的内容在首屏还是被迫滚动才能找？ | 辅助统计/低频管理最醒目，主要内容缺席或被推远；重排默认内容和动作层级 |
| 归组与阅读路径 | 为完成一次判断，需要从哪些区域拼接对象、条件、状态、依据和动作？ | 关联信息拆散、重复标题/说明、同等按钮竞争；按对象/判断重新邻近和去重 |
| 密度与空间 | 哪块拥挤、哪块空闲；列宽/高度由实际内容还是机械等高撑开；正文/列表实际能看几项？ | 短内容占大块空列而主内容挤窄/落到屏外；修正布局约束。留白能帮助阅读时保留，不设统一面积比例 |
| 底色与容器层级 | 背景画布、主内容、目录/辅助和浮层分别是什么语义表面；哪一层承担边界？ | 同类表面一页透明一页白、逐条嵌套卡片、边框重复；查公共组合/主题 owner 及局部CSS覆盖 |
| 字体、对齐与控件 | 标题/正文/元信息能区分吗；同组控件基线、高度、图标/间距、主题与状态一致吗？ | 用小字/浅字掩盖拥挤、标签和控件错位、局部自造状态色；回到项目排版/token/组件变体 |
| 默认、收纳与变化 | 哪些内容常驻的理由成立；收起后知道在哪里找、关键错误/条件是否仍可见；打开后挤压/遮挡哪里？ | “更多”静默藏问题、低频表单长期占位、展开后主内容无法对照；连同摘要、入口与返回一起修正 |

**C. 做两种对照，不以单页自洽代替全局统一。**

- 与采用稿/规则比较区域顺序、主辅关系、工具栏行数、列宽/行高、间距和收纳。不能因控件功能可用或“视觉偏好不同”自行放弃已约定关系。
- 与同类已统一页面并排比较控件、骨架、表面层级/底色、标题/正文级别、密度、语义色和响应式。统一指同类语义遵守相同合同，不要求编辑器、阅读页、监控台都长成一个模板。
- 对每项差异定位到公共组件/组合、主题/token、页面CSS或实际容器条件。相同语义出现重复局部实现时，优先回公共维护归属修正；业务特例明确条件与适用范围。不能每页补一个颜色值或另套一层卡片遮住根因。
- 不能直接比较的条件须说明；宽度不同时仍可检查归组/表面，不能据此宣布列宽保真通过。新布局借用示例内容时，必须再覆盖实际可取得的正常多项和长内容，不可只用短样例。

**D. 主动尝试推翻初步结论。** 按改动选择最可能失败的条件，如一项对多项、长标题、空/错误、选中/禁用、展开后返回、窄工作面；字号/缩放仅在明确相关缺陷或专项授权时验证。实际操作并检查完整滚动内容，不能只截首屏或避开有问题的区域。无需凑出固定数量缺陷；没有发现缺陷时也要说明检查了哪些关系、为什么符合标准。

**E. 根据结论继续工作。**

- 必验项有明确偏差：判“不通过”，写入原项并修正→原路径复验。不能把 after 截图直接交用户发现问题。
- 环境、数据或交互证据不足：判“待验”，写明具体缺口；不把“不知道”写成“没有问题”。
- 全部受影响必验关系满足：才可判该范围“视觉通过”，并独立核对功能/交互。
- 用户反馈推翻旧结论：保留原失败证据，重开原项、改正对外状态及待交付候选。新增规则/道歉不等于问题已修复。

合格记录示例：“一项决定被等高分栏撑至旁栏三条请求的高度，目标列表落在下屏；违背主列连续阅读和内容自适应；不通过，改主列堆叠后以同容器/数据复验。”不合格记录：“已看宽窄深浅截图，布局清晰，无溢出，视觉通过。”

### 基本可读性与操作条件

- 主要任务和次要信息的层级是否清楚，主操作会不会被说明文字淹没？
- 否定、条件、金额等关键正文是否被单行标签、省略号或折叠隐藏？
- 长名字、多语言、长列表、图片和正文是否可读、可滚动，操作仍可触达？
- 浮层、吸底条、软键盘等是否遮挡当前内容/焦点？真实软键盘未测则单列。
- 控件是否有可理解标签、足够点击空间；状态是否同时用文字/图标表达？
- 使用项目的字体、间距、图标和控件体系；不要因个人喜好另造视觉语言。
- 如有触摸/拖拽任务，检查相应输入方式和可用替代路径；不要把鼠标成功当触摸成功。

Web 可访问性参考 [WCAG 2.2](https://www.w3.org/TR/WCAG22/) 中与本次界面有关的文字对比、重排、键盘、焦点、拖拽替代和目标尺寸条款。检查具体门槛时读取原文及适用例外；抽查几项不能宣布整个产品符合 WCAG。

## 最小证据包

每个证据记录：时间、代码/制品版本、环境、角色身份、数据性质、视口/设备、操作序列、实际结果、截图/日志路径、能证明什么与不能证明什么。

| 观察 | 能支持 | 不能支持 |
| --- | --- | --- |
| 静态代码确认存在保存处理 | 实现中存在该路径 | 用户可以发现入口、保存确实成功 |
| fixture 在实际页面展示错误 | 该输入下的错误 UI | 真实服务故障恢复和真实模型质量 |
| 双独立身份在实际服务读回状态 | 本次条件下共享状态/权限表现 | 多设备压力、弱网、所有角色覆盖 |
| 桌面浏览器 390px 截图并点按钮 | 该视口布局及鼠标命中 | iOS 软键盘、触摸手势、真机性能 |
| imagegen 生成候选 | 设计意图可视化 | 已实现、已发布或可操作 |
| 发布构建在指定设备/负载下测得性能 | 该条件下的加载、交互或服务指标 | 所有设备的流畅性、真实月度可用性或未测规模容量 |

这些证据互补，不是一个可以靠单项高等级证据替代其余维度的排名。
